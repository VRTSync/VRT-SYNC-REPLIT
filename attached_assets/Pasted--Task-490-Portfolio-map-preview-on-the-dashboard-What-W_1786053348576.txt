# Task #490: Portfolio map preview on the dashboard

## What & Why

The client dashboard is entirely tabular — KPIs, a week grid, group cards, a location table. The one thing that makes VRTSync obviously different from a spreadsheet, the map, is two clicks away. The approved dashboard design (`marketing/portal-mockups/01-hero-portfolio-dashboard.png`) puts the Location Snapshot and a portfolio map side by side at the bottom of the page, which is also the image the marketing site leads with.

## Done looks like

- The bottom section of the dashboard is a two-column row: **Location Snapshot** table on the left, a **Portfolio Map** panel on the right at a fixed 470px column width, both stretching to equal height.
- The map panel has a normal `.panel-head` reading "Portfolio Map" with the hint "N locations".
- The map renders through **`common/map-render.js`** — the shared renderer from #464. No new rendering path, no direct Leaflet calls, no second copy of the pin logic. If the shared module needs a smaller preview mode, add it there and let every surface have it.
- Pins are the same colour-by-group treatment the Portfolio Map page already uses, with the same amber ring for a location that has an open work order. A compact legend sits bottom-left listing each group and its count.
- Clicking a pin navigates to that location's detail page. Clicking the panel header's map area anywhere else navigates to the full Portfolio Map route.
- The map is **not interactive beyond that**: no zoom controls, no satellite toggle, no expand button, no scroll-wheel zoom. It is a preview, and a map that hijacks the page scroll on a dashboard is a bug.
- On a narrow viewport the two columns stack, map below table.
- The dashboard's existing KPI row, week hero, and group cards are unchanged.

## Steps

1. Restructure the bottom of `renderDashboard` into the two-column row. `.two-col` already exists in `portfolio.css` and is used by `branch-detail.js` — reuse it if its proportions suit, otherwise add a dashboard-specific grid in the same idiom.
2. Reuse the data already in hand. The dashboard fetch returns branches with coordinates and open-WO counts; `/api/portfolio/map` returns the same shape the map page uses. **Prefer whichever avoids a second network call on dashboard load** — and if that means the dashboard endpoint needs two more fields, add them there rather than issuing a second request.
3. Instantiate the shared renderer against a container in the map panel. Disable interaction handlers explicitly (`scrollWheelZoom`, `dragging`, `doubleClickZoom`, keyboard) rather than relying on defaults.
4. Fit the viewport to all mapped locations once, on first render. Locations without coordinates are simply absent — do **not** place them at a default position, and do not surface the "not yet mapped" list here (the Portfolio Map page already owns that).
5. Wire pin click → `PortfolioRouter.navigate('branch-detail', …)`, and the surrounding map area → the map route.
6. **Verify.**
   - Dashboard loads with the map populated; pin count matches the KPI location count minus unmapped.
   - Exactly one network request more than before, or zero.
   - Scrolling the page over the map scrolls the page.
   - Pin click opens the right location; map click opens the Portfolio Map.
   - An org with zero mapped locations shows an empty-state panel, not a grey box or a console error.
   - The Portfolio Map page and the branch-detail map still behave exactly as before — this is the shared renderer's whole purpose, so a regression there is the thing to watch for.
   - Idle the dashboard for five minutes: the map does not re-initialise itself (depends on #481 and #486).

## Out of scope

- Any change to the Portfolio Map page.
- Full-screen or satellite in the preview.
- Clustering.
- Showing task or asset pins — this preview shows locations only.
