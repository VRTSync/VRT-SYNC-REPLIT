# Task #362: Phase 1.5 schema — service visit status + invoice status

## What & Why

Two metrics that nearly every dashboard needs are currently uncomputable, and `GET /api/admin/dashboard` correctly returns `null` for them:

- **Service reliability** (on-time %, missed services): `service_visits` rows only exist once someone logs a visit, so an absent row can mean "not done" or "not yet generated" — indistinguishable.
- **Invoice aging** (unpaid, paid, overdue): `invoices` has no status, due date, or paid date.

This task is SCHEMA ONLY — columns, enums, indexes, migration. No routes, no UI, no scheduler/job logic, no backfill of business meaning. Same shape and safety rules as #361.

## Core principles (do not deviate)

- Extend existing tables; no new tables in this task.
- A visit row represents one expected occurrence of a schedule on a date. `service_visits.serviceDate` + the existing unique `(schedule_id, service_date)` index already model this.
- **Never invent financial facts.** Legacy invoices get `status = NULL` (unknown), not an assumed value.

## Done looks like

- `lib/db/migrations/0006_service_and_invoice_status.sql` applies cleanly and is a no-op on re-run.
- `pnpm run typecheck` passes with zero new errors; server boots; `pnpm --filter @workspace/api-server run build` run so migrations copy to `dist/migrations/`.
- Existing HOA behavior byte-for-byte unchanged (login each role, admin dashboard, community map + tasks, service calendar).
- Manual SQL verification passes (see Steps 5).
- `replit.md` gains one line under Architecture decisions describing visit status semantics.

## Out of scope

- Generating/materializing expected visit rows from schedules (that is the follow-up task, #363).
- Any change to `GET /api/admin/dashboard` or its `null` fields.
- Any UI, mobile, or export change.
- Changing `invoices.cost` from `double precision` (noted as tech debt; a money-as-float fix is its own migration).
- Any modification to existing columns, enums, or indexes beyond the additive items below.

## Steps

### 1. `service_visits` — status + skip reason

- New enum `serviceVisitStatusEnum` = `pgEnum("service_visit_status", ["scheduled","completed","skipped","missed"])`.
- Add columns to `serviceVisits`:
  - `status` — `service_visit_status NOT NULL DEFAULT 'scheduled'`
  - `skipReason` — `text NULL` (why a visit was skipped: weather, access, client request)
- Semantics to document in `replit.md`: `scheduled` = expected, not yet performed; `completed` = performed (`completed_at` set); `skipped` = intentionally not performed, reason recorded; `missed` = expected date passed with no completion and no reason.

### 2. `service_visits` — backfill existing rows factually

In the same migration, after adding the column:

```sql
UPDATE service_visits SET status = 'completed' WHERE completed_at IS NOT NULL AND status = 'scheduled';
```

Rows with `completed_at IS NULL` stay `scheduled` — do NOT mark any legacy row `missed`; we cannot know that retroactively.

### 3. `service_visits` — index for range queries

- Add index on `(community_id, service_date)` — dashboards query by community + date window. Keep the existing unique `(schedule_id, service_date)` index untouched.

### 4. `invoices` — status, dates, number

- New enum `invoiceStatusEnum` = `pgEnum("invoice_status", ["draft","submitted","approved","paid","void"])`.
- Add columns to `invoices` (ALL nullable, NO default):
  - `status` — `invoice_status NULL` (NULL = legacy/unknown; new invoices set it explicitly)
  - `invoiceNumber` — `varchar NULL`
  - `dueDate` — `date NULL`
  - `paidAt` — `timestamp NULL`
- Add index on `status`.
- **Do not backfill any existing invoice row.** Legacy rows keep `status = NULL` so aging metrics can exclude "unknown" rather than assert unpaid.

### 5. Migration file + verification

- Generate via `pnpm --filter @workspace/db run migrate:generate`, then hand-edit so every statement is guarded: `ADD COLUMN IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, and enum creation via `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN null; END $$;` (or `CREATE TYPE IF NOT EXISTS` if supported by the target PG version — match whatever pattern `0000_baseline.sql` uses for enum creation).
- Confirm `meta/_journal.json` entry matches the file name, and set its `when` timestamp to the actual current date (0005 was written with a 2025 date — do not repeat that).
- Manual SQL checks after applying:
  - Insert a visit with no status → defaults to `scheduled`.
  - Existing completed visits now report `completed` (count matches `SELECT COUNT(*) FROM service_visits WHERE completed_at IS NOT NULL`).
  - `SELECT COUNT(*) FROM invoices WHERE status IS NULL` equals total legacy invoice count (nothing was backfilled).
  - Insert an invoice with `status='paid'`, `paid_at=now()` → succeeds.
  - Re-run the migration → no errors, no changes.
