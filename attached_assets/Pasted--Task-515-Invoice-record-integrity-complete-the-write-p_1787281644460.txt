## What & Why

The `invoices` table is well shaped for a contractor's billing history. The **write path is not** — `createInvoice()` cannot set four of the table's own columns, there is nowhere to put the reference number the import needs as an idempotency key, and money is stored as floating point while every other financial figure in the app is integer cents.

None of this is visible to a client. All of it determines whether the billing record VRT relies on is trustworthy.

Full analysis: `docs/invoice-schema-fit-2026-08-11.md`.

## ⚠️ Correction before you start item 1

The plan states these fields are "silently ignored". **Verify that before treating it as the baseline** — the evidence says they may already persist.

- Both `insertInvoiceSchema` and `updateInvoiceSchema` (`schema.ts` ~1066, ~1082) **already include** `status`, `invoiceNumber`, `dueDate`, and `paidAt`.
- The route does `storage.createInvoice(parsed.data)` — no field stripping.
- `createInvoice` does `db.insert(invoices).values(data)` — **no key filtering**. Drizzle maps whatever known columns are present on the object.
- TypeScript's excess-property check applies to object *literals*, not to a variable like `parsed.data`. So this compiles, and at runtime the extra fields reach `.values()` and are inserted.

So `status` and `invoiceNumber` most likely **already work through the API today**. The real defect is narrower: the signature lies about what the function accepts, so any caller constructing a literal cannot pass them, and nobody reading the type knows they exist.

`paidAt` is the interesting one — Zod types it as a string, the column is `timestamp`. That may throw at runtime rather than persist. `dueDate` is a string into a `date` column, which Drizzle handles.

**Do this first:** POST an invoice with `status` and `invoiceNumber` set, against the current code, and report what lands in the row. Then fix from a known baseline.

Why it matters: the verify step below says *"create an invoice with invoice number and status and verify both persist."* If they already persist, that test passes before any change is made and proves nothing. Establish the baseline or the verification is theatre.

Also worth noting: **the admin invoices UI never sends these fields at all** — no `invoiceNumber`, `status`, `dueDate`, or `paidAt` in `admin/pages/invoices.js`. So even once the write path is correct, there is no way to set them from the UI. That is out of scope here, but it means the import is the only thing that will populate them, and a human cannot correct one afterwards. Flag it as a follow-up.

## 1. `createInvoice` cannot write half the table

```ts
export async function createInvoice(data: {
  communityId; contractor; completionDate; serviceType; cost;
  notes?; pdfObjectKey?; attachmentLabel?; attachmentLayerId?;
}): Promise<Invoice>
```

The table has `invoice_number`, `status`, `due_date`, and `paid_at`. The typed input omits all four. `updateInvoice` omits them too.

**Fix:** extend both to accept the full set. `status` is already a valid enum (`draft/submitted/approved/paid/void`); `invoice_number`, `due_date`, and `paid_at` are plain columns.

**Do not work around this by inserting directly against the table from the import script.** The gap is real and the next caller inherits it. Close it at the source.

While there, check every existing caller still compiles and behaves — the new fields must be optional so nothing currently calling `createInvoice` changes behaviour.

## 2. No `reference_number` column

The import's idempotency key is `invoice_number + reference_number + community_id + completion_date`, verified collision-free across all 139 rows. `reference_number` has nowhere to live.

**Fix:** add `reference_number varchar` to `invoices`, and a **unique index** on the four-column key:

```sql
CREATE UNIQUE INDEX invoices_source_line_unique_idx
  ON invoices (invoice_number, reference_number, community_id, completion_date)
  WHERE invoice_number IS NOT NULL AND reference_number IS NOT NULL;
```

Partial, so hand-entered invoices without those fields are unaffected.

This is the difference between idempotency the application *tries* to enforce and idempotency the database *guarantees*. Given the import writes to production, take the guarantee.

## 3. No import-batch marker

Tasks get `origin = 'master_bill_import'`, so a bad task batch is deletable in one statement. Invoices have no equivalent — identifying a bad invoice batch would mean reverse-engineering it from dates and invoice numbers.

**Fix:** add `source varchar` and `source_batch varchar` (or a single `import_batch` — pick one and say why). Populate with the importer's name and billing period. Index `source_batch`.

A batch must be deletable by one predicate, from both tables, with no orphans.

## 4. `cost` is floating point for money

`invoices.cost` is `doublePrecision`. Every other financial figure in the app is integer cents — `tasks.estimate_cents`, and `invoiced_cents` in the admin dashboard, which is literally `SUM(cost * 100)`, multiplying a float and hoping.

139 rows summing to $53,120.90 will drift in the last cents, and that drift surfaces in an admin figure.

**This one needs a judgment call, so make it deliberately:**

1. **First, count the existing rows.** `SELECT COUNT(*) FROM invoices`. Report the number before doing anything.
2. **If the table is small or empty** — likely, since nothing has been importing invoices — migrate `cost` to `cost_cents integer` properly: add the column, backfill `ROUND(cost * 100)`, update all readers and writers, drop `cost`. One source of truth, matching the rest of the app.
3. **If the table has meaningful production data**, stop and report the count rather than migrating under time pressure. Propose it as its own task.

**Do not add `cost_cents` alongside `cost` and leave both.** Two columns holding the same money in different units is exactly the parallel-implementation pattern this project has explicitly rejected before. Either migrate cleanly or don't touch it.

## Done looks like

- `createInvoice` and `updateInvoice` accept every column the table has, with the new fields optional.
- `reference_number` exists, with the partial unique index on the four-column source key.
- A batch marker exists and is indexed; one predicate deletes a batch cleanly from both `invoices` and `tasks`.
- `cost` is either migrated to integer cents with all readers updated, or explicitly deferred with the row count reported.
- Migration ships as a file under `lib/db/migrations/` with a journal `when` **greater than** the current `MAX(created_at)` in `__drizzle_migrations` — an earlier `when` is silently skipped and the migration never runs. Server rebuilt so migrations copy to `dist`.
- The admin invoices page and monthly report still work unchanged.
- No client-facing surface changes. The enterprise portal does not read invoices and must not start.

## Verify

- Create an invoice through the admin UI with an invoice number and status → both persist and display.
- Insert two rows with the same invoice number, reference, community and date → **the second is rejected by the database**, not by application code. Test with direct SQL, not through the API.
- Insert two rows sharing three of the four → succeeds.
- A hand-entered invoice with no invoice number or reference still saves — the partial index does not catch it.
- Delete a batch by its marker → all rows gone, no orphans, other invoices untouched.
- If `cost` was migrated: existing values equal `ROUND(old * 100)` to the cent, the admin monthly report totals match what they showed before, and `invoiced_cents` no longer multiplies a float.
- `/api/admin/migrations` reports `inSync: true`.

## Out of scope

That denial is accidental, not designed. It is not urgent while nothing grants that membership, but it should be hardened before the commercial tier has a second client. Raise it as its own task.
