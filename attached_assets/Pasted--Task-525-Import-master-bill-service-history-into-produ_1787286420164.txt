## ⚠️ Three corrections to the handover draft — read before implementing

A revised version of this spec was drafted for handover. Three of its instructions reference columns that do not exist or reintroduce a defect that already blocked this project once. All three verified against `schema.ts` at `9a4af6c`.

### 1. `AND t.origin NOT IN (...)` reintroduces the #514 null bug

The draft's step 3 says to filter the work-orders query with `AND t.origin NOT IN (...)`.

**`tasks.origin` is nullable** (`schema.ts:151`, no `.notNull()`), and `NULL NOT IN ('master_bill_import')` evaluates to **NULL**, not TRUE — so a `WHERE` clause drops every null-origin row. Null is the origin of ordinary contractor and admin work. That predicate would empty the client Work Orders page of almost everything real while doing nothing about the imports.

This is the exact defect found in #514 on 2026-08-11 and fixed there. The shared helper already emits the correct form:

```ts
function importOriginExclude(tableAlias: string = 't'): string {
  return IMPORT_ORIGINS
    .map(o => `${tableAlias}.origin IS DISTINCT FROM '${o}'`)
    .join(' AND ');
}
```

**Call `importOriginExclude('t')` and interpolate its output. Do not hand-write a `NOT IN`.**

### 2. `tasks` has no `invoice_number`, `reference_number` or `source_batch` column

The draft specifies task idempotency as *"skip if the task with the same `origin + invoice_number + reference_number + community_id` already exists"* and an undo keyed on `tasks.source_batch`. **None of those three columns exists on `tasks`** — they are `invoices` columns (`schema.ts:1053`, `1058`, `1062`).

Use **`tasks.importFingerprint`** instead. It is purpose-named for this, indexed (`tasks_import_fingerprint_idx`, `schema.ts:170`), and already the established pattern — `contractImporter.ts:235` computes one the same way.

Set it to a value that serves both idempotency and batch delete:

```
importFingerprint = '{source_batch}:{invoice_number}:{reference_number}:{pnc_code}'
```

- **Idempotency:** exact-match lookup before insert.
- **Undo:** `DELETE FROM tasks WHERE origin = 'master_bill_import' AND import_fingerprint LIKE 'master_bill_2026_05:%'`.

The index is **not unique**, so the pre-insert check is the guarantee — do the lookup inside the same transaction. If a hard guarantee is wanted, add a partial unique index in a migration, subject to the journal `when` rule.

**Do not encode the batch in `tasks.title`.** The draft floats this; the title renders in the UI and would show a batch marker to the client.

### 3. Do not set `status`, `due_date` or `paid_at` on invoices

The draft omits these fields entirely, which risks an implementer supplying a plausible-looking default. See the section below — leaving all three null is deliberate and required.

### Also worth knowing

- **`contractImporter.ts` already exists** and parses xlsx, computes fingerprints, and inserts tasks with preview/commit modes. It is wired to admin routes at `routes.ts:4637` and `4658`. It is built around user-supplied column mappings rather than a fixed layout, so reusing it here is likely more work than it saves — but **read it first** and reuse `computeFingerprint`'s approach at minimum. Do not create a second, divergent import idiom.
- The draft's claim that unmatched origins are labelled `'HP'` is **out of date**. `routes.ts` now reads *"origin = 'HOA' / null / other → 'Contractor report' (generic — not branded)"*. The label is already fixed; the flooding problem is not.

## What & Why

The pilot org's portal shows zero services logged, because no service history has ever been entered. Meanwhile three master bills from High Plains Property Maintenance record every service actually performed on the PNC branches, with dates, descriptions, invoice numbers, and amounts.

Importing them makes the pilot portal show real work instead of empty panels, and puts the billing records where they belong.

**This writes to production.** Every requirement about dry runs, idempotency, and reversibility below is load-bearing, not ceremony.

### ⚠️ Required: normalise 20 out-of-period contract dates

The May and June bills date their **Monthly Landscape Contract** lines to the *first of the following month* — one day past their own billing period. July dates its contract lines to the last day of the month, which is correct. This is an error in the source files, confirmed against the raw cells (plain text strings, not misconverted dates) and against each sheet's own header:

| Bill | Header period | Contract lines dated | Correct? |
|---|---|---|---|
| May | May 1 – May 31, 2026 | `2026-06-01` | ✗ |
| June | June 1 – June 30, 2026 | `2026-07-01` | ✗ |
| July | July 1 – July 31, 2026 | `2026-07-31` | ✓ |

**Every service must fall inside the billing period of the bill it appears on.** Normalise the affected rows to the last day of their period: May → `2026-05-31`, June → `2026-06-30`.

Exactly **20 rows** are affected, all of them Monthly Landscape Contract lines, one per contracted branch per month:

| Bill | Row | PNC | As written | Normalised |
|---|---|---|---|---|
| May | 5, 10, 16, 21, 24, 28, 31, 40, 43, 47 | FB01, FB02, FB08, FB15, FB16, FB1B, FB36, FB4F, FB5F, FB65 | `2026-06-01` | `2026-05-31` |

**Implement this as a general rule, not a hardcoded row list:** if a row's service date falls outside its bill's billing period, clamp it to the nearest period boundary. Then **assert that exactly 20 rows were clamped** and print each one. If the count is not 20, or a clamped row is not a Monthly Landscape Contract line, stop — the input differs from what was validated.

Normalisation applies to `invoices.completion_date`. **Note that all 20 clamped rows are Monthly Landscape Contract lines, and contract lines no longer produce a `task_completions` row** — so in practice no completion date is ever clamped. Clamp anyway, as a general rule: if a future bill puts an extra-work line outside its period, the rule must catch it.

This also removes a symptom flagged earlier: with contract lines no longer producing completions, **"Last service" can no longer read `2026-07-01`** for branches whose most recent record was a mis-dated June contract line.

### ⚠️ Imported tasks will flood the client Work Orders page unless excluded

Verified against `566ac51`. `GET /api/portfolio/work-orders` selects **every task for the org with no filter**:

```sql
FROM tasks t
JOIN org_coms c ON c.id = t.community_id
ORDER BY t.created_at DESC
```

No predicate on `status`, `origin`, or anything else. The route then partitions rows into open / closed / cancelled in JS.

So importing 139 tasks with `status = 'completed'` puts **139 rows into the "closed" bucket of the client Work Orders page** — every historical bill line re-presented as a work order the client supposedly raised.

Two things make that worse than merely noisy:

1. **The reference is meaningless.** The route derives `ref = 'WO-' + first 8 chars of the task uuid`. A billed service line would show as `WO-A1B2C3D4` — a work-order number that never existed.
2. **The source label is wrong.** Source is derived from origin, and the branches are `origin === 'client'` → "PNC request", **everything else → `'HP'`**. So `master_bill_import` falls through to `'HP'`, presenting historical billing as though HP raised 139 work orders.

**A work order is a request that was tracked. A billed service line is history.** These records already surface correctly as Services Logged, Last Service, Recent Activity, and Service History. Showing them a second time as closed work orders double-represents the same work and clutters the one screen the client uses for actionable items.

**Required:** exclude `origin = 'master_bill_import'` from the client Work Orders query. Use the same shared exclusion constant #514 introduces for the photo rate — do not define a second list of import origins.

Check the same question for the **flow-diagram counts and the sidebar badge** on that page. The badge counts awaiting-approval only, so it should be unaffected, but confirm rather than assume.

## What gets written

Each detail row produces an `invoices` row. **Rows that are not `Monthly Landscape Contract` additionally produce a `tasks` + `task_completions` pair** — see the split table above.

**1. An `invoices` row** — the billing record of truth. **All 139 rows.**

```
community_id      resolved from PNC Code
contractor        'High Plains Property Maintenance'
completion_date   Service Date
service_type      the bill's own wording, verbatim (free text column, no enum)
cost              Amount
notes             Description
invoice_number    Invoice #
reference_number  Reference #        (idempotency key component, added by #515)
source            'master_bill_import'
source_batch      e.g. 'master_bill_2026_05'
status            LEAVE NULL         ← see below
due_date          LEAVE NULL
paid_at           LEAVE NULL
```

#### Do not set `status`, `due_date`, or `paid_at`

**Decision 2026-08-20: VRTSync is not bookkeeping software and will not track paid/unpaid here.**

`invoices` in this product is a **service record that happens to carry an amount** — what work was done, where, when, by whom, for how much. It is not an accounts-receivable ledger, and the moment it starts asserting payment state it acquires an obligation to be *right* about payment state, which nothing in this system can honour. There is no payment event, no reconciliation, and no source of truth for settlement. A `status` column that says `'paid'` because an importer guessed is worse than a null one.

The schema permits this cleanly — `status: invoiceStatusEnum("status")` at `schema.ts` is **nullable with no default**, as are `due_date` and `paid_at`. Leaving all three null is a legal row, not a workaround.

**Concretely:** omit these three fields from the insert. Do not substitute `'draft'`, `'approved'`, or any other enum value as a "neutral" placeholder — every one of them is a claim. Null is the honest value, and it is the one that reads correctly if a real billing integration is ever added.

If any UI surfaces an invoice status for these rows, it should render blank — not "Unpaid", which is itself an assertion.

**2. A `tasks` row plus a `task_completions` row** — what makes the portal show it. **Only the 110 non-contract rows.**

```
tasks
  community_id    same
  title           Description, trimmed
  status          'completed'
  origin          'master_bill_import'
  estimate_cents  round(Amount * 100)

task_completions
  task_id         the task above
  completed_by    see below
  completed_at    Service Date
  notes           '{Service Type} · Invoice {Invoice #} · Ref {Reference #}'
```

Both are needed. `invoices` is never read by the client portal (billing is deliberately excluded from it); `task_completions` is what `Services Logged`, `Last Service`, and `Recent Activity` actually count. That asymmetry is exactly why the contract lines can be held out of `task_completions` without losing a cent of revenue from the billing record.

## Non-negotiables

**Dry run by default.** Running the script with no flags **prints and writes nothing**. It reports: rows parsed, rows matched to a community, rows skipped and why, per-branch counts and totals, the resolved `completed_by` user, and a full sample of what a row would become. It writes only when passed an explicit confirm flag.

**Idempotent.** Re-running must not double anything. The natural key is `invoice_number + reference_number + community_id + service_date`, **verified collision-free across all 139 rows** (139 rows → 139 distinct keys). Store the reference on the invoice row (add a column, or fold it into `notes` in a parseable form) and skip any row already present. Say which approach you took.

Note `LC` appears 29 times as a bare reference; it is unique only in combination with the other three fields, so do not key on reference alone.

**Reversible.** Tag everything with a batch identifier — `tasks.origin = 'master_bill_import'` plus the billing period. Include a documented delete for a batch. If a code mapping turns out wrong, the fix must not be archaeology.

**Fail loudly on ambiguity.** If a PNC Code matches zero communities, or more than one, stop and report — do not guess from the building name. A wrong community assignment is worse than an unimported row.

**Transactional per bill.** One billing period, one transaction. A partial import is the worst outcome.

## Steps

1. Script at `scripts/import-master-bill.ts` (or wherever the repo keeps one-offs). Arguments: path to the xlsx, billing period label, `--confirm` to write.
2. Parse `Service Detail` only, from row 5.
3. Resolve each PNC Code against `communities.code` **scoped to the pilot organization**. Report the mapping table before doing anything else.
4. Resolve or create the `completed_by` user.
5. Dry-run report.
6. On `--confirm`: insert inside a transaction, skipping rows already imported.
7. Print a post-import summary and the exact command to undo the batch.
