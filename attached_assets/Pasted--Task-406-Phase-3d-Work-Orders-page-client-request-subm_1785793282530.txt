# Task #406: Phase 3d — Work Orders page + client request submission

## What & Why

The portfolio is read-only today. This slice makes it **two-way**: PNC can see every open item across their branches, watch it move through the lifecycle, and **submit a new request** themselves — which lands as a task in the existing system that HP's crews see in the mobile app.

This is the page that turns the portal from a report into a service.

## 🎨 Design reference

`mockups/pnc-branch-portfolio-v4.html` → **Work Orders** page. Match:

- Navy anchor band containing the **pipeline flow**: `Flagged by HP → Awaiting approval → Scheduled → Completed`, each step a chip with a count, the "awaiting approval" step highlighted amber.
- KPI row: Awaiting Your Approval / Scheduled / Flagged by HP / Closed (30d).
- Filter chip row + search.
- **Open Work Orders** table: Work Order ref, Branch, Item (title + subtitle + photo count), Source, Opened (date + days open), Status chip, Estimate.
- **Recently Closed** table below: ref, branch, item, opened, closed, days open.
- Closing callout describing the lifecycle.

## Core principles

- **A work order IS a task** (established in #361). Do not create a parallel table or a separate concept — everything here reads and writes `tasks` scoped to the org's communities.
- Client submissions must be indistinguishable, to crews, from any other task: they appear in the mobile app, on the map if located, and in exports.
- Escaping via `VRTUtils.esc`. Org scoping on every endpoint.

## Done looks like

- `#/work-orders` (sidebar: "Work Orders", with an amber count badge when items await approval) renders the pipeline band, KPIs, filters, and both tables from live data.
- **Client can submit a request**: a "+ Submit Request" button opens a form (branch selector, title, description, optional photo upload, optional map location) that creates a task in that branch.
- Submitted requests immediately appear in the Open table with source "PNC request" and status reflecting the task's real state.
- **Approval action**: work orders carrying an `estimateCents` with no `approvedAt` show an **Approve** button; approving sets `approvedAt`/`approvedBy` and moves the item out of "Awaiting approval". A short confirm step precedes it (this is a money decision).
- Empty states are honest — a portfolio with no work orders shows a single quiet message, not empty tables.
- Cross-org access impossible: submitting to, approving, or reading another org's task returns 403.
- Dashboard's "Open Work Orders" KPI links here.

## Out of scope

- Editing or cancelling a submitted request (later).
- Attaching documents (photos only, via the existing attachment/object path).
- Contractor-side changes, mobile app changes, notifications/emails.
- Any change to task status enums or the task schema beyond using existing columns.

## Steps

### 1. API — read (`artifacts/api-server/src/routes/routes.ts`)

`GET /api/portfolio/work-orders` (`requireClientOrAdmin`, org-resolved):

```json
{
  "pipeline": { "flagged": 0, "awaitingApproval": 0, "scheduled": 0, "completed30d": 0 },
  "open": [ { "id","ref","branchId","branchCode","branchName","title","description",
              "source","status","openedAt","daysOpen","estimateCents","approvedAt","photoCount" } ],
  "closed": [ { "id","ref","branchId","branchCode","title","openedAt","closedAt","daysOpen","photoCount" } ]
}
```

- `open` = non-completed tasks in the org's communities; `closed` = completed in the last 30 days.
- **`ref`**: use the task id short form unless a human-facing reference already exists — do **not** invent a new numbering scheme or add a column. State in a comment what was used.
- **`source`**: derive from existing data (e.g. `origin`, or `createdBy`'s role — client-created vs contractor/admin-created). If it cannot be determined reliably, return `null` and render "—" rather than guessing.
- `daysOpen` computed in SQL; `photoCount` from attachments linked to the task/completion.

### 2. API — submit (`POST /api/portfolio/work-orders`)

- `requireClientOrAdmin`, org-scoped: body `{ communityId, title, description, latitude?, longitude?, priority? }`.
- Validate `communityId` belongs to the caller's org (403 otherwise) before anything else.
- Create via the **existing task creation storage path**, setting `createdBy` to the client user and an `origin` value that marks it client-submitted (reuse an existing origin convention if one exists — check `tasks.origin` values in use first and report what you found).
- Photos: accept an optional array of already-uploaded object keys using the existing upload/confirm flow (`POST /api/objects/upload` → `confirm`); do not build a new upload mechanism.
- Return the created task in the same shape as an `open` row.

### 3. API — approve (`POST /api/portfolio/work-orders/:taskId/approve`)

- `requireClientOrAdmin`, org-scoped; 403 if the task's community isn't in the caller's org.
- Sets `approvedAt = now()`, `approvedBy = session user`. Idempotent: approving twice returns the current state, not an error.
- Does **not** change task status — approval is a client decision, scheduling stays with HP.

### 4. Page — `public/portfolio/pages/work-orders.js`

- Register `PortfolioRouter.register('work-orders', …)`; add to `NAV_ITEMS` with a badge showing `awaitingApproval` when > 0.
- Render per the mockup: pipeline band, KPI row, filter chips (Open / Awaiting approval / Scheduled / Closed) + search, Open table, Recently Closed table, closing callout.
- Row click → branch detail for that branch (deep link with the work order highlighted if cheap; otherwise just the branch).
- **Approve** button on qualifying rows → confirm dialog showing branch, item, and estimate → POST → optimistic row update + toast.

### 5. Submit Request form

- "+ Submit Request" in the page header opens a modal: **Branch** (select from `PortfolioState.branches`), **Title**, **Description**, optional **photos**, optional **location** (reuse `/pin-picker.html` in an iframe, same as other portals do).
- Client-side validation with inline errors; disable submit while in flight; on success close, toast, and prepend the new row.
- On 403/409, show the message inline — never a toast that discards the user's typing.

### 6. Verify

- As the PNC client user: submit a request against FB02 → appears in Open with source "PNC request"; confirm the same task is visible to an admin in the admin hub and would reach crews (check it appears in `/api/tasks` for that community).
- Approve a work order with an estimate → moves out of Awaiting approval; approving again is a no-op, not an error.
- Cross-org: attempt to submit with another org's `communityId` → 403; attempt to approve another org's task → 403.
- Empty portfolio → quiet empty state, no broken tables.
- Admin with `?org=` → same behavior, and confirm actions are attributed to the admin user, not the client.
- Dashboard "Open Work Orders" tile links to this page and the counts agree.
