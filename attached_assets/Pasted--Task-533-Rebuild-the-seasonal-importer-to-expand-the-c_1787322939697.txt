# Task #533: Rebuild the seasonal importer to expand the contract task list

*Fixes `seasonalImporter.ts`, which cannot consume the file it exists to import. Full diagnosis in `reviews/review-2026-08-21-import-batch.md`. Verified at `2cb0c9d`.*

## What & Why

`seasonalImporter.ts` was built as a **dated-visit importer**: one spreadsheet row becomes one service visit, with the row supplying the community code and the service date.

`Contract Task List - VRT.xlsx` supplies neither. Its columns are **Ticket Title, Ticket Type, Priority, Start Date, End Date, Frequency, Total Visits, Description** — 18 rows describing a seasonal programme that applies identically to all 11 branches. There is no community column because every branch gets the same list, and no service date because the dates are **derived** from the season window and the visit count.

Uploading it fails at the column-mapping step: the required columns do not exist to map.

### The direction was inverted

The module header states:

```
- Every service_date must be a Wednesday (day-of-week = 3)
```

#518 said to **generate** evenly-spaced Wednesdays. The implementation **validates** that supplied dates are Wednesdays. Same for the 2026 rule — specced as an assertion on the source file's *start dates*, implemented as a per-row *service date* check.

**The input is 18 rows. The output is 803 records.** That expansion is the entire job and it is absent — no handling of `Frequency`, `Total Visits`, or a season window exists anywhere in the module.

## The fix, precisely

### 1. Drop the column-mapping step for this mode

The contract task list has a fixed layout, like the master bill. Read it by header name, assert the eight expected columns are present, and fail with a clear message naming any that are missing.

**Seasonal becomes 3 steps: Upload → Preview → Commit.** Delete `SeasonalColumnMappings` and every parameter that carries it. The `parse` route keeps `upload.single("file")`; `preview` and `commit` take the parsed rows only.

### 2. Assert the source file on load

- Exactly **18 rows**
- Every **Start Date in 2026**
- Every **End Date after its Start Date**

Any failure is a blocking error naming the offending row. This is what stops someone uploading `Contract Task List - VRT (ORIGINAL uncorrected).xlsx`, which has 2025 starts and one row ending before it starts.

### 3. Split the 18 rows by Frequency

| Frequency | Rows | Destination |
|---|---|---|
| `Weekly` / `Monthly` | 3 | `service_schedules` + `service_visits` |
| `One-Time` | 15 | `tasks` (+ `task_completions` where past) |

Applied to **all 11 communities in the pilot org** — resolve them by `organization_id`, not from a column in the file.

### 4. Generate the visit dates

Season is `2026-04-01 → 2026-10-31`, taken from the recurring rows' own Start/End dates. It contains **31 Wednesdays**.

For a schedule with *n* total visits, select Wednesdays by index:

```
idx = round(i × 30 / (n − 1))   for i in 0 .. n−1
```

| Ticket Title | serviceType | n | First | Last | completed / scheduled |
|---|---|---|---|---|---|
| Weekly Landscape Maintenance | `mowing_visit` | 26 | 2026-04-01 | 2026-10-28 | **18 / 8** |
| Roundup Spot Spray | `landscape_service` | 26 | 2026-04-01 | 2026-10-28 | **18 / 8** |
| Bluegrass Edging Service | `landscape_service` | 6 | 2026-04-01 | 2026-10-28 | **4 / 2** |

Every date is a Wednesday, no two collide, and the last lands in the season's final week. A visit is `completed` if its date is on or before today, `scheduled` otherwise.

**`serviceType` comes from the mapping above, per schedule.** The current `commitSeasonal` hardcodes `general_service` for every schedule; that is wrong and loses the distinction the This Week grid needs.

### 5. One-time tasks carry windows, not dates

The 15 one-time rows become `tasks` with `window_start` / `window_end` / `due_date` from the sheet's Start and End dates, `origin = 'contract_schedule'`, `ticket_type` verbatim, and priority mapped `High→high, Medium→medium, Critical→urgent, Core→medium, Ongoing→medium`.

The 8 whose `window_end` has passed also get a `task_completions` row so they count toward Services Logged.

### 6. Fix the task idempotency key

The current key is `seasonal:<scheduleId>:<serviceDate>:<titleHash>`. **One-time seasonal tasks have neither a schedule nor a single service date**, so that shape cannot express them.

Use `schedule_instance_key = 'contract_schedule:{communityId}:{Ticket Title}'` — unique per branch per contract task, which is exactly the grain. The existing `tasks_schedule_instance_key_idx` unique index enforces it.

Visit idempotency is already correct: `(schedule_id, service_date)` via `service_visits_schedule_date_idx`. Keep it.

### 7. Three defects in `commitSeasonal` to fix while rebuilding

**a. Silent skips.** The loop does `if (!dateObj || dateObj.getFullYear() !== 2026 || !isWednesday(dateObj)) continue;` and the same for unresolved communities. Rows vanish with no report. **Every skip must be counted and surfaced**; a commit that quietly drops rows cannot be reconciled afterwards.

**b. N+1 community lookup.** `SELECT id FROM communities WHERE code = $1 LIMIT 1` runs inside the per-row loop. Resolve all communities once, before the loop.

**c. `LIMIT 1` hides ambiguity.** `previewSeasonal` correctly blocks when a code matches two communities; `commitSeasonal` silently takes the first. **Preview and commit must agree.** Resolve by `organization_id` and fail on ambiguity in both.

- **The parse/preview/commit split and the three routes.** Signatures change; the shape does not.

- **The transaction wrapper**, the `import_batches` row, and the batch-history/undo path from #532.

- **`masterBillImporter.ts` and its routes.** Working and reviewed; untouched by this.

- **The `import_batches` schema** — migration `0017` is applied; no new migration should be needed.
- **`origin = 'contract_schedule'`**, and its membership in the work-orders exclusion.
- **The Wednesday crew day and even-spread cadence.** The reasoning is settled in `docs/contract-task-list-validation-2026-08-11.md`; do not re-derive it.
