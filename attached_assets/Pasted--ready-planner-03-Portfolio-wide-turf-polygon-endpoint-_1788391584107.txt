# ready-planner-03: Portfolio-wide turf polygon endpoint

*Awaiting a number. Spec 03 of 10 — see [`ready-planner-00-index.md`](ready-planner-00-index.md).*

## What & Why

`GET /api/admin/xeriscape/community/:communityId/polygons` (`routes.ts:1399`) resolves bluegrass polygons for **one community**. The goal-seek in spec 09 has to rank every convertible area across the whole portfolio against each other, so it needs them all in one response.

This spec adds that endpoint and fixes a reliability problem the current one already has.

## ⚠️ The existing endpoint drops polygons silently

It loads `bluegrass_area` assets, then resolves each to a GeoJSON feature by trying `f.id`, `properties.featureId`, `properties.id`, `properties.featureRef`, and finally a name match (`:1446-1457`). **Assets that resolve to nothing are dropped from `features` with no error.** The route returns `assetsFound` and `featuresResolved` — and the client ignores both.

A goal-seek that quietly omits a third of the portfolio's turf produces a confidently wrong answer. **Unresolved assets must be visible.**

## Acceptance criteria

**New endpoint**

```
GET /api/portfolio/water-savings/polygons?organizationId=<id>
```

- [ ] **`requireClientOrAdmin`**, not `requireAdmin`. Resolve the org with the existing `resolvePortfolioOrg(req)` (`routes.ts:5919`) exactly as `/api/portfolio/analytics` (`:6125`) does. Do not hand-roll org resolution.
- [ ] Returns every non-archived `bluegrass_area` asset across **all communities in that org**, as a `FeatureCollection`.
- [ ] Each feature's `properties` carries at minimum:

```
id, name, area_sqft, communityId, communityName
```

`communityId` and `communityName` are new and non-negotiable — the goal-seek groups results by location and the table shows the location on every row.

- [ ] Response envelope:

```json
{ "type": "FeatureCollection", "features": [...],
  "assetsFound": 0, "featuresResolved": 0,
  "unresolved": [{ "assetId": "...", "name": "...", "communityId": "...", "communityName": "..." }],
  "byCommunity": [{ "communityId": "...", "communityName": "...",
                    "assetsFound": 0, "featuresResolved": 0, "sqFtResolved": 0 }] }
```

- [ ] **Extract the resolution logic into one shared helper** used by both the existing admin route and this one. Two copies of the featureRef fallback chain is exactly the drift this project has been bitten by. Do not leave a parallel implementation.
- [ ] `req.log.info` the org id, community count, `assetsFound`, `featuresResolved`.

**Coverage must surface in the UI**

- [ ] Where `featuresResolved < assetsFound`, the consuming page shows a caveat naming the count — *"14 turf areas could not be located on a map layer and are excluded."* Not a console warning.
- [ ] Assets with a null or zero `area_sqft` are **resolved but flagged**, not silently included as zero. Zero-area turf skews a cost-effectiveness ranking toward infinity.

**Performance**

- [ ] **One round trip per table**, not per community. Batch: assets by `inArray(communityId, ids)`, properties by `inArray(assetId, ids)`, layers by `inArray(id, layerIds)` — the existing route already does this shape for one community; keep it for N.
- [ ] Parse each `mapLayers.geojsonData` **once** and cache by layer id within the request. The current code builds `featureMap` per layer already; make sure that survives the multi-community loop rather than re-parsing per asset.
- [ ] Log total elapsed ms. Ten communities and ~500 assets should be well under a second; if it is not, say so rather than shipping it quietly.

## Files likely involved

- `artifacts/api-server/src/routes/routes.ts` — new route near the other `/api/portfolio/*` handlers (`:5919+`), and refactor of `:1399-1470`
- possibly `artifacts/api-server/src/storage.ts` for the shared resolver

## What must NOT change

- **The existing admin route's response shape.** The admin planner still calls it; spec 07 is what eventually retires it.
- Asset, map layer or asset-property schema. **No migration in this spec.**
- `bluegrass_area` remains the only type considered. Broadening to other turf types is a separate decision.

## How to verify

- [ ] Call it as a `client_admin` on the PNC org → features across **10 communities**, `assetsFound` matching the bluegrass count.
- [ ] `sum(features[].properties.area_sqft)` reconciles with the Landscape bluegrass total on the Analytics page. **These must agree** — two different numbers for portfolio turf on two pages is worse than either being wrong.
- [ ] Call it as a `client_admin` of **a different org** → none of PNC's polygons. Then call with an explicit `?organizationId=<PNC>` as that same non-PNC user → **403 or empty, never PNC data.**
- [ ] Archive one bluegrass asset → it disappears and `assetsFound` drops by one.
- [ ] Break one asset's `featureRef` → it moves into `unresolved`, `featuresResolved` drops, and the caveat appears in the UI.
- [ ] Confirm one resolver implementation: `grep -n "featureRef" artifacts/api-server/src/` should show the fallback chain **once**. Confirm the files exist before trusting an empty result.
- [ ] Compare the admin route's output for one community against the new route filtered to that community — **identical features**.

## Out of scope

- Consuming the endpoint (specs 08 and 09).
- Fixing the underlying data for unresolved assets — this spec surfaces them, it does not repair them.
- Non-turf asset types.
