# Task #366: Phase 2a — organization scoping + admin provisioning endpoints

## What & Why

Phase 1 added the commercial-tier schema (#361, #365). Nothing can use it yet: there is no way to create an organization, attach branches to it, or restrict a client user to their own branches.

This task adds (a) org-scoping middleware mirroring the existing HOA pattern, and (b) admin-only CRUD so VRT staff can provision an organization, its branches, its groups, and its client users. **No client-facing portal, no portfolio UI, no dashboards** — those are later phases.

End state: an admin can create the PNC organization with its 11 branch communities and a `client_admin` user, and that user can authenticate and hit a single scoped "who am I / what do I own" endpoint. Nothing else changes.

## Core principles (do not deviate)

- A branch IS a community — branch creation goes through the existing community creation path with org fields attached. Do NOT add a separate branch creation flow that bypasses `storage.createCommunity`.
- Org scoping mirrors `enforceHoaScoping` in `artifacts/api-server/src/auth.ts`. Same shape, same error style, same 403 semantics.
- **Commercial branches must not leak into HOA-facing lists.** Any existing endpoint that returns "all communities" for HOA/PM/contractor consumption must exclude rows where `organization_id IS NOT NULL`, unless the caller is an admin.
- Admin-only provisioning. No self-serve signup, no client-side org creation.

## Done looks like

- Admin can, via API: create an org; create a branch community under it (with `code`, `address`, `city`); list/update/delete orgs and branches; create/rename/delete branch groups and set membership; create a `client_admin` user bound to an org.
- A `client_admin` user calling any scoped endpoint can only reach their own org's data; cross-org access returns 403.
- `GET /api/portfolio/me` returns the caller's org and their branches (id, name, code, city) — the single endpoint the future portal boots from.
- Existing HOA/PM/contractor endpoints behave identically, and commercial branches do not appear in their community lists.
- `pnpm run typecheck` passes; server boots; no changes to `artifacts/api-server/src/shared/` or mobile.

## Out of scope

- Any web-portal UI, shell, or page (Phase 3+).
- Portfolio dashboard aggregates, work-order approval endpoints, groups comparison math (Phase 2b and later).
- Mobile app changes.
- Seeding real PNC data (done manually by admin after this lands, or as a separate seed task).
- Changing any existing route's behavior other than the HOA-list exclusion described above.

## Steps

### 1. Scoping middleware — `artifacts/api-server/src/auth.ts`

- Add `isClientRole(role)` → `role === 'client_admin'` (mirrors `isHoaRole`/`isMapCreatorRole`).
- Add `requireClient(req,res,next)` — 401 if unauthenticated, 403 unless role is `client_admin`; attaches `(req as any).currentUser`.
- Add `enforceOrgScoping(req,res,next)` modeled directly on `enforceHoaScoping`:
  - resolve the user; if not `client_admin`, `next()` (admins unaffected)
  - determine target community from `req.params.id || req.params.communityId || req.query.communityId || req.body?.communityId`
  - if a community is targeted, load it and 403 unless `community.organizationId === user.organizationId`
  - if an `organizationId` is present in params/query/body, 403 unless it matches the user's
- Session: store `organizationId` on the session at login the same way `hoaCommunityId` is stored today, to avoid a user lookup per request. Follow the existing pattern exactly (declaration in the `express-session` module augmentation).

### 2. Storage functions — `artifacts/api-server/src/storage.ts`

Add, following existing naming/style:

- `createOrganization(data)`, `getOrganizationById(id)`, `listOrganizations()`, `updateOrganization(id, data)`, `deleteOrganization(id)`
- `listBranchesByOrg(orgId)` — communities where `organization_id = $1`, ordered by `code`
- `createBranch({ organizationId, name, code, address, city, description })` — **calls the existing `createCommunity` then updates the org fields**, or extends `createCommunity` to accept them; do not duplicate community-creation logic
- `updateBranch(communityId, { code, address, city })`
- `createBranchGroup(orgId, { name, color, sortOrder })`, `listBranchGroups(orgId)`, `updateBranchGroup(id, data)`, `deleteBranchGroup(id)`
- `setBranchGroupMembers(groupId, communityIds[])` — replaces membership in one transaction
- `getPortfolioForUser(userId)` — returns `{ organization, branches[] }` for a client user

### 3. Admin provisioning routes — `artifacts/api-server/src/routes/routes.ts`

All `requireAdmin`. Validate bodies with drizzle-zod schemas from `@workspace/db`; 400 with `error.flatten()` on failure, matching existing routes.

```
POST   /api/admin/organizations
GET    /api/admin/organizations
GET    /api/admin/organizations/:id
PATCH  /api/admin/organizations/:id
DELETE /api/admin/organizations/:id

GET    /api/admin/organizations/:id/branches
POST   /api/admin/organizations/:id/branches      → creates a community with organizationId set
PATCH  /api/admin/branches/:communityId           → code/address/city only

GET    /api/admin/organizations/:id/groups
POST   /api/admin/organizations/:id/groups
PATCH  /api/admin/groups/:groupId
DELETE /api/admin/groups/:groupId
PUT    /api/admin/groups/:groupId/members         → body { communityIds: string[] }
```

Duplicate `(organization_id, code)` must return **409** with a clear message, not a 500 (the partial unique index will throw — catch it).

### 4. Client user creation

- Extend the existing admin user-creation path to accept `role: 'client_admin'` plus `organizationId` (required when role is `client_admin`; reject with 400 otherwise).
- Login flow: no change to credentials handling; only ensure `organizationId` lands on the session for client users.

### 5. `GET /api/portfolio/me`

- `requireClient` + `enforceOrgScoping`.
- Returns `{ organization: { id, name }, branches: [{ id, name, code, city, address }], groups: [{ id, name, color, branchIds[] }] }`.
- This is the only non-admin endpoint in this task.

### 6. HOA-facing list exclusion

- Audit endpoints that return community lists for non-admin roles (e.g. `GET /api/communities` and any HOA/PM/contractor community pickers). Where the consumer is not an admin, filter out `organization_id IS NOT NULL`.
- **List every endpoint you changed in the PR description** so the reviewer can verify nothing was missed. If an endpoint is ambiguous, leave it and flag it rather than guessing.

### 7. Verify

- Manual: create org → create 2 branches → create a group with both → create `client_admin` user → log in as that user → `GET /api/portfolio/me` returns exactly those 2 branches. Attempt to read a community from another org → 403. Attempt duplicate code in same org → 409.
- Log in as `hoa_admin`, `property_manager`, `contractor`, `admin` and confirm their community lists are unchanged except that commercial branches are absent for non-admins.
- `pnpm run typecheck` passes; `pnpm --filter @workspace/api-server run build` succeeds.
