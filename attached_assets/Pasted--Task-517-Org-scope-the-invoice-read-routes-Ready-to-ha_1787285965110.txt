# Task #517: Org-scope the invoice read routes

*Ready to hand over. Number assigned locally — see the note in #516.*

## Severity: correctness and clarity, not security

**Read this before treating it as urgent.** I previously described this as "any authenticated portfolio user can read invoices across orgs." **That was wrong**, and I am correcting it in the spec rather than quietly dropping it. Verified against `9a4af6c`:

`enforceOrgScoping` is registered globally at `routes.ts:111` (`app.use("/api", enforceOrgScoping)`), so it runs on the invoice routes already. For a client role it resolves `communityId` from params, query or body and rejects anything belonging to another organization:

```ts
if (community.organizationId !== userOrgId) {
  res.status(403).json({ message: "Access denied: community belongs to a different organization" });
  return;
}
```

**Cross-tenant reads are blocked.** There is no leak to fix. What follows is about two endpoints that don't work correctly for client users and one latent trap.

## What & Why

`GET /api/invoices` and `GET /api/invoices/:id` predate the organization model and scope by **community membership only**:

```ts
export async function isUserMemberOfCommunity(userId, communityId) {
  const [row] = await db.select().from(communityMembers)
    .where(and(eq(communityMembers.userId, userId),
               eq(communityMembers.communityId, communityId)));
  return !!row;
}
```

That helper reads `community_members` and never consults `users.organizationId` or `communities.organizationId`. A `client_admin` gets org access through `organizationId` — that is the entire mechanism of the commercial tier — and is not necessarily a row in `community_members`.

So the current behaviour for a PNC portfolio user is:

| Request | Result today | Why |
|---|---|---|
| `GET /api/invoices` (no param) | **400** | handler requires `communityId` for non-admin, non-HOA roles |
| `GET /api/invoices?communityId=<own branch>` | **403** | passes `enforceOrgScoping`, then fails the membership check |
| `GET /api/invoices?communityId=<other org>` | **403** | correctly blocked by `enforceOrgScoping` |
| `GET /api/invoices/:id` | **404 "Community not found"** | see the trap below |

Three of those four are wrong or misleading. Only the last row of the table is the behaviour anyone intended.

### The latent trap — `enforceOrgScoping` reads `req.params.id` as a community id

`auth.ts:142`:

```ts
const communityId = req.params.id || (req.params as any).communityId
                    || req.query.communityId || req.body?.communityId;
```

On `/api/invoices/:id`, `req.params.id` is an **invoice** id. The middleware looks it up with `getCommunityById()`, finds nothing, and returns **404 "Community not found"** — for an invoice that exists, to a user whose org owns it.

This affects every `/api/<thing>/:id` route for client roles, and there are roughly 60 of them. **Today it is latent**, because every route a `client_admin` is meant to call uses `:communityId` or `:taskId` — I checked all 18 `/api/portfolio/*` routes and none uses a bare `:id`. It stops being latent the first time someone adds one.

**Do not "fix" any of this by adding `community_members` rows for client users.** That would make org isolation depend on membership rows being maintained correctly forever, with no constraint enforcing it — trading a clear 403 for a silent, unenforced invariant. Fix the scoping, not the data.

## Acceptance criteria

### 1. `GET /api/invoices` gains a client-role branch

Insert **before** the existing membership fallback, mirroring how `/api/portfolio/*` resolves an org:

- If `isClientRole(user.role)`:
  - Resolve `orgId` from `user.organizationId` fresh from the DB, session as fallback only — the same precedence used at `routes.ts:5673`.
  - `403` if the user has no `organizationId`.
  - If `?communityId=` is supplied, return invoices for that community. `enforceOrgScoping` has already proven it belongs to the org; do not re-derive that check, and do **not** call `isUserMemberOfCommunity`.
  - If `?communityId=` is absent, return invoices for **every community in the org**, newest `completion_date` first.

### 2. `GET /api/invoices/:id` gains the same branch

For client roles, authorize by comparing the invoice's community's `organizationId` against the user's, replacing the `isUserMemberOfCommunity` call on that path. Non-client roles keep their existing behaviour unchanged.

### 3. `enforceOrgScoping` stops guessing that `:id` means a community

Narrow line 142 so `req.params.id` is only treated as a community id on routes where it is one. Preferred: drop `req.params.id` from the fallback chain entirely and rely on `req.params.communityId`, `req.query.communityId` and `req.body.communityId`.

**Before changing it, confirm no route depends on the current behaviour** — `/api/communities/:id` and its sub-routes are the ones to check, since there `:id` genuinely is a community. If any do, keep `req.params.id` but only apply it when the path starts with `/api/communities/`. Say which approach you took and why.

### 4. New storage function

`getInvoicesByOrganization(organizationId)` — join `invoices` to `communities`, filter on `communities.organization_id`, order by `completion_date DESC`, and return the same shape as `getInvoices` including `communityName`. Do not modify `getInvoices`.

## What must NOT change

- **`requireClient` and the overall contract of `enforceOrgScoping`.** `auth.ts:177` carries an explicit instruction not to modify them; item 3 narrows one fallback inside `enforceOrgScoping` and must not alter its cross-org rejection logic.
- **Admin and HOA behaviour on both routes.** Admin still reads any community or all of them; HOA roles stay pinned to `hoaCommunityId`.
- **`POST` / `PUT` / `DELETE /api/invoices`** — all `requireAdmin`, all out of scope.
- **The client portal must not start showing billing.** This makes the API correct for the org; it does not put invoices on a client screen. Billing is deliberately excluded from the portfolio portal and that stays true.
- `getInvoices` keeps its current signature and behaviour.
