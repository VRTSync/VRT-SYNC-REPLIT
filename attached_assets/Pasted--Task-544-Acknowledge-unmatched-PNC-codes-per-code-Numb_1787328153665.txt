## What & Why

The master bill preview correctly blocks Commit when a PNC code has no matching community:

```
Blocking Errors — Commit is disabled
• PNC Code "FB45" — no matching community found in database
```

That guard is working exactly as intended and **must not be removed.** An unmatched code is the signal that catches a typo, a renamed branch, or a genuinely missing property — the failure mode where real service history gets filed against the wrong location and looks completely normal afterward.

But there is a legitimate case it currently has no answer for: **the code is unmatched because the property is genuinely not in the portfolio.**

`FB45 / 88th and Wadsworth` is that case. One line ever — a $425 planter-box install on 2026-05-18 — and no community record. *Decision 2026-08-21: import without it.*

Right now the only ways forward are to create a community that shouldn't exist, or to weaken the check. Neither is acceptable.

## The fix: acknowledge, don't downgrade

When a code is unmatched, the preview lists it as now, **and offers a per-code checkbox**:

> ☐ `FB45` — 1 row, $425.00 — **skip these rows and import the rest**

Commit stays disabled until **every** unmatched code is either resolved or explicitly ticked. Ticking is a deliberate act per code, not a global override.

**Do not add a "skip all unmatched" button**, and do not convert the blocking error into a warning. The value of this check is that it forces a human to look at each unmatched code individually. Twelve unmatched codes should be twelve decisions, or an obvious sign that something is wrong with the file.

## Acceptance criteria

1. **Preview** returns unmatched codes as a distinct, structured list — code, row count, dollar total, and the Excel row numbers — separate from other blocking errors.
2. **The UI renders a checkbox per unmatched code**, showing its row count and amount so the cost of skipping is visible before it's chosen.
3. **Commit remains disabled** while any unmatched code is unacknowledged, and while any *other* blocking error exists. Acknowledging an unmatched code must not clear unrelated errors.
4. **The acknowledged list is sent with the commit request** and re-validated server-side. A commit naming codes the preview didn't flag is rejected — the checkbox is a UI affordance, not the authority.
5. **Acknowledged rows are recorded as skips**, with the reason `acknowledged_unmatched`, in the same skipped-rows report as `GRAND TOTAL`. They appear in the post-import summary and in the batch record. They are never silently dropped.
6. **Re-uploading resets acknowledgements.** A new file means new decisions.
7. **The totals shown must reflect the skips.** With FB45 acknowledged, May previews as **45 rows / $17,950.04**, not 46 / $18,375.04. A preview that shows a total it isn't going to write is worse than no total.

## What must NOT change

- **The blocking behaviour for unacknowledged codes.** Default stays blocked.
- **Every other assertion** — `GRAND TOTAL` filtering, the 20 date clamps, the 29 contract-only rows, the First Bank guard, idempotency keys.
- **The mapping table stays prominent.** This adds to it; it does not replace reading it.
- **Seasonal mode.** Its community resolution is org-wide and has no per-row codes; leave it alone.
