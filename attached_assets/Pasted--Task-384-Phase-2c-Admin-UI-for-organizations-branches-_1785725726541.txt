# Task #384: Phase 2c — Admin UI for organizations, branches, groups, and client users

## What & Why

The commercial-tier schema and API exist (#361, #365, #368, #372), but there is no interface for managing any of it. The existing Communities page can create a community but cannot set an organization, code, address, or city, and there is no Organizations page or group editor at all — those fields are reachable only through raw API calls.

This task adds admin-hub UI so VRT staff can provision and manage commercial clients by hand: create an organization, add its branches one at a time, organize branches into groups, and create the client user who will log into the portal.

**No client-facing portal work** — that is Phase 3.

## Core principles

- **Branch creation lives on the org detail page**, not the Communities page. HOA and commercial creation flows stay visually separate.
- The Communities page only gains a **read-only indicator** showing which communities belong to an organization.
- Follow existing admin-hub patterns exactly: `AdminRouter.register(...)`, `AdminAPI.apiFetch`, `VRTUtils.esc` for all interpolated data, existing `.page-header` / `.btn` / `.form-input` / modal / toast conventions, styles added to `admin.css` using existing variables.

## Done looks like

- New sidebar entry **Organizations** between "Communities" and "Users" in `admin-shell.html`.
- **Organizations list page** (`#/organizations`): table of orgs with name, kind, contact, branch count, created date; "+ New Organization" opens a modal (name, kind, contact name, contact email); row click → org detail.
- **Org detail page** (`#/organizations/:id`): header with org name + edit/delete actions; three sections — Branches, Groups, Client Users.
  - **Branches**: table (code, name, address, city, actions). "+ Add Branch" modal (name, code, address, city). Inline edit and delete per row. Duplicate code shows the API's 409 message as a form error, not a toast-and-lose-your-input.
  - **Groups**: list of groups with color swatch and member count. Create/rename/recolor. Membership editor = checkbox list of the org's branches; save calls the members endpoint (replace-set).
  - **Client Users**: list of `client_admin` users bound to this org; "+ Add Client User" modal (username, display name, password) posting to the existing admin users endpoint with `role='client_admin'` and this org id.
- **Delete guards surfaced properly**: deleting an org with branches returns 409 — show the API message ("reassign or delete them first"), don't just fail silently.
- Communities page shows an org badge (e.g. a small chip with the org name) on commercial communities; no editing of org fields there.
- All data rendered through `VRTUtils.esc`; no `innerHTML` interpolation of API data without escaping.
- No console errors; `pnpm run typecheck` and build pass; nothing outside the web-portal artifact and `admin-shell.html` changes.

## Out of scope

- The client-facing Branch Portfolio (Phase 3).
- Bulk import / CSV of branches (manual creation is the point of this task).
- Mobile app changes.
- Any new API endpoints — everything needed exists from #368. If something is genuinely missing, stop and report rather than adding endpoints ad hoc.

## Steps

1. **Shell + route**: add the `Organizations` nav item to `artifacts/web-portal/templates/admin-shell.html` and register `<script src="/admin-static/pages/organizations.js">` (and `organization-detail.js` if split) in the existing script block, after `communities.js`.
2. **Organizations list** — new `public/admin/pages/organizations.js`, `AdminRouter.register('organizations', …)`. Data from `GET /api/admin/organizations`; branch counts via `GET /api/admin/organizations/:id/branches` (or a single call if one already returns counts — check before adding N+1 fetches; if it would be N+1, fetch counts lazily per row after initial render and say so in the notes).
3. **Org detail** — `AdminRouter.register('organizations/:id', …)` following the existing `community-detail.js` pattern for a detail route with sub-sections. Wire all CRUD to the endpoints from #368:
   - `GET/PATCH/DELETE /api/admin/organizations/:id`
   - `GET/POST /api/admin/organizations/:id/branches`, `PATCH /api/admin/branches/:communityId`
   - `GET/POST /api/admin/organizations/:id/groups`, `PATCH|DELETE /api/admin/groups/:groupId`, `PUT /api/admin/groups/:groupId/members`
   - `POST /api/admin/users` with `role='client_admin'` + `organizationId`
4. **Communities page badge** — in `communities.js`, when a community has `organizationId`, render a small chip with the org name. Requires org names; fetch `GET /api/admin/organizations` once and map ids → names (single extra request, no per-row fetches).
5. **Styles** — add to `admin.css` using existing CSS variables only. No new fonts, no inline `<style>`, no new libraries.
6. **Verify** — Create an organization; add 3 branches including one with a duplicate code (expect an inline 409 error); edit a branch's address; create 2 groups and assign branches to each; create a client user; confirm `GET /api/portfolio/me` as that user returns the org, branches, and groups. Attempt to delete the org (expect 409), delete its branches, then delete the org successfully. Confirm the Communities page shows org chips on those branches and that HOA/PM/contractor logins do not see them at all.
