# Task #492: Admin UI for group sets

## What & Why

#488 shipped the group set concept: the `branch_group_sets` table, `branch_groups.set_id`, a one-group-per-set constraint, and `GET /api/portfolio/group-sets`. #489 shipped the client-facing Groups page that reads it.

**Nothing can create a set or assign a group to one.** The three pilot sets exist only because the migration seeded them, and it deliberately assigned groups to `Region` only when a group name was an unambiguous compass word. Everything else was left `set_id NULL` on the reasoning that a wrong assignment is worse than an empty one.

That reasoning was right, and it left a hole: those groups now render under **"Ungrouped"** on the client's Groups page and there is no way to move them. The client-facing screen looks broken while behaving exactly as designed.

This closes it, using the admin surface that already manages groups.

## Where this goes

`artifacts/web-portal/public/admin/pages/organization-detail.js` already has a Groups panel with Add / Edit / Members / Delete per group, backed by:

```
GET    /api/admin/organizations/:id/groups
POST   /api/admin/organizations/:id/groups
PATCH  /api/admin/groups/:groupId
DELETE /api/admin/groups/:groupId
PUT    /api/admin/groups/:groupId/members
```

Extend that panel. Do not build a new page.

## Done looks like

**API**

- `GET /api/admin/organizations/:id/group-sets` — sets for the org, each with `id`, `name`, `sortOrder`, and `groupCount`. `requireAdmin`.
- `POST /api/admin/organizations/:id/group-sets` — create. Body `{ name, sortOrder? }`. Rejects a duplicate name for the org with **409** and a message naming the conflict, not a raw constraint error (`branch_group_sets_org_name_unique`).
- `PATCH /api/admin/group-sets/:setId` — rename, reorder.
- `DELETE /api/admin/group-sets/:setId` — deletes the set. Groups in it fall back to `set_id NULL` via the existing `ON DELETE SET NULL`, which the propagate trigger from #488 pushes down to member rows automatically. **Confirm that trigger fires on the cascade** and say so in the implementation notes; if it does not, the member rows need an explicit cleanup.
- `PATCH /api/admin/groups/:groupId` accepts `setId` (a set id, or `null` to unassign) in addition to the fields it takes today.

**Assignment must not be able to strand data.** Moving a group into a set can violate the one-per-set constraint if two of its members already sit in another group of that set. The DB will reject it. Handle it: return **409** with a message naming the conflicting group and how many locations are affected, e.g. *"3 locations in this group already belong to North in the Region set. Move them or choose a different set."* Do not let this surface as a 500.

**UI**

- The Groups panel groups its rows **by set**, with a subheading per set in `sortOrder` and an **Ungrouped** section last. Sets with no groups still show, so an empty set is visibly available as a destination.
- A **Set** control on each group row, next to Edit, that reassigns the group. A plain select of the org's sets plus "Ungrouped" is sufficient; this is an internal tool.
- Set management: add, rename, reorder, delete, in the same modal idiom the existing group modals use.
- Deleting a set warns that its groups become Ungrouped and names how many.
- A 409 from either endpoint renders the server's message in the modal. It is already written for a human; do not replace it with "Failed to".

**Nothing changes on the client-facing side.** `/api/portfolio/groups`, `/api/portfolio/group-sets`, and the Groups page are read-only consumers and must not be touched.

## Steps

1. Storage: `getGroupSets(orgId)`, `createGroupSet`, `updateGroupSet`, `deleteGroupSet`. Follow the naming and shape of the existing `createBranchGroup` / `updateBranchGroup` / `deleteBranchGroup`.
2. Routes: the five endpoints above, all `requireAdmin` with org resolution matching the sibling routes.
3. `PATCH /api/admin/groups/:groupId`: allow `setId` through. It currently whitelists `name`, `color`, `sortOrder` — extend that whitelist explicitly rather than passing the body through.
4. 409 handling: reuse the `isUniqueViolation` helper #488 added for `branch_group_members_one_per_set_idx`, and add the set-name unique index to it.
5. UI: regroup `renderGroups` by set, add the Set control, add the set-management modals.
6. **Then use it.** Assign the pilot org's real groups to Region, Service Tier, and Branch Format. This task is not done until the client Groups page shows no Ungrouped section for the pilot org, or until what remains there is genuinely meant to be ungrouped.

## Verify

- Create a set, rename it, reorder it, delete it. Groups in a deleted set become Ungrouped and their member rows' `set_id` goes NULL. Check the member rows directly, not just the UI.
- Assign a group to a set. Its members' `set_id` updates via the propagate trigger.
- Force the conflict: two groups in one set sharing a location. The 409 message names the conflicting group and the count.
- Duplicate set name in the same org returns 409, not 500.
- Same set name in a *different* org succeeds.
- A group can be moved back to Ungrouped.
- Client Groups page reflects every change on reload, and the "Ungrouped" section disappears once everything is assigned.
- A client user cannot reach any of these endpoints.

## Out of scope

- Bulk assignment or drag-and-drop.
- Set management from the client portal. Sets are configuration, and configuration is admin-only.
- Changing the one-per-set constraint or the triggers from #488.
- Colors on sets. Groups carry the color; sets are organizational.
