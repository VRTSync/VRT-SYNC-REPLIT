### 1. I was wrong: the one-group-per-set invariant is ALREADY implemented

My earlier draft of this spec said the sibling-removal rule "is not enforced by a constraint — **the application must enforce it**," and listed it as the most important work in the task. **That was wrong**, and the handover draft's step 2 is right to say "verify" rather than "build."

`storage.ts:4014` already does it, inside a transaction, with comments explaining exactly why:

```ts
export async function setBranchGroupMembers(groupId, communityIds) {
  await db.transaction(async (tx) => {
    const [group] = await tx.select().from(branchGroups).where(eq(branchGroups.id, groupId));
    await tx.delete(branchGroupMembers).where(eq(branchGroupMembers.groupId, groupId));
    if (communityIds.length > 0) {
      // Move semantics: assigning a location to a group in a set removes its
      // existing membership in any other group of the same set, in the same
      // transaction.  Reassigning North → Central must not 500.
      if (group?.setId) { /* deletes sibling memberships */ }
      // set_id is intentionally NOT supplied — a DB trigger derives it
      await tx.insert(branchGroupMembers).values(...);
    }
  });
}
```

**So the work here is to call it, not to write it.** The new `PUT /api/portfolio/groups/:groupId/members` route must pass through to this function unchanged. Do not reimplement move semantics in the route, and do not add a second transaction around it.

The verification step still matters — reassigning a location from North Metro to Central and confirming exactly one membership row per set is the test that proves the route is wired to the right function.

### 2. Step 8's navigation call is wrong in three ways

The draft says:

> `PortfolioRouter.navigate('locations', { group: groupId })`

- **The route is named `branches`, not `locations`.** `portfolio.js:44` is `{ route: 'branches', label: 'Locations' }` — "Locations" is the display label only, per the #487 rename which deliberately left the plumbing alone. `navigate('locations', …)` targets a route that was never registered.
- **The signature is `navigate(routeName, pushState, params)`** (`portfolio-router.js:14`). Passing the object as the second argument puts it in the `pushState` slot; `params` then falls back to `{}` and the group id is silently dropped.
- **`navigate` only serialises `params.id` into the path** (line 21-23). A `{ group: … }` param never reaches the URL, so it cannot survive a reload or be linked to.

**And the destination does not accept a filter yet.** `branches.js:312` is `function renderBranches(container, _params)` — the params argument is underscore-prefixed and unused, and line 329 hardcodes the initial filter to `'all'`. The client-side group filter exists (`branches.js:266-268` matches on `b.groupIds`), but nothing can set it from outside the page.

So step 8 is not a one-line link. It requires:

1. `navigate('branches', true, { group: groupId })`, and
2. `renderBranches` reading `params.group` and passing it as the initial `activeFilter` instead of `'all'`, and
3. a decision on how the filter appears in the URL, since `navigate` only handles `id`. Simplest is to extend the path handling to accept `branches/group/<id>`, or to read a query string. **State which was chosen.**

If that is more than this task should carry, drop step 8 and raise it separately — but do not ship the one-liner, because it will silently navigate to a dead route.

## What & Why

The Groups page renders and then does nothing. There is no way to create a group, rename one, change its colour, delete it, or move a location between groups. Verified at `9a4af6c`: **`pages/groups.js` is 214 lines containing zero click handlers, zero buttons, zero links.** The only `addEventListener` in the file is the `DOMContentLoaded` used to register the route.

The page even ships a control that pretends to work. `groups.js:132`:

```js
// Inert in this slice: renders, not clickable, no handler.
cards += '<div class="gcard add">+ New group</div>';
```

A **"+ New group" card renders in the grid and does nothing when clicked.** That is worse than an absent feature — it is a visible affordance that lies, and it is the first thing anyone tries.

The page's own subtitle says *"organize locations the way your business is structured."* Right now the client cannot organize anything.

## The blocker: every group write route is admin-only

All seven write routes live under `/api/admin/*` behind `requireAdmin`:

```
POST   /api/admin/organizations/:id/groups        6914
PATCH  /api/admin/groups/:groupId                 6935
DELETE /api/admin/groups/:groupId                 6980
PUT    /api/admin/groups/:groupId/members         6991
POST   /api/admin/organizations/:id/group-sets    7040
PATCH  /api/admin/group-sets/:setId               7063
DELETE /api/admin/group-sets/:setId               7086
```

A `client_admin` cannot call any of them. The read side (`GET /api/portfolio/groups`, `/api/portfolio/group-sets`) exists; the write side was never built for clients.

**Do not relax `requireAdmin` on the existing routes.** Those take an org id in the path, which is safe for an admin and unsafe for a client. Add parallel `/api/portfolio/*` routes that resolve the org **from the session only** and never accept it as a parameter, so cross-org writes are impossible by construction rather than by check.

## ⚠️ The invariant that must not break: one group per set per location

Group sets exist so each set is an independent dimension — Region, Service tier, Site size. A location belongs to **exactly one** group within any given set.

**Assigning a location to a group must remove it from every other group in that same set, in the same transaction.** Without this, a location can be both "North Metro" and "West Metro", and every consumer breaks: the Analytics page's and/or filtering becomes ambiguous, the Locations page's group chip picks one arbitrarily, and the Portfolio Map colours a pin by whichever row it read first.

It is not enforced by a database constraint — `branch_group_members` is unique on `(group_id, community_id)`, which prevents duplicate membership in the *same* group but permits membership in two groups of the same set.

**Correction: `setBranchGroupMembers` at `storage.ts:4014` already enforces it in a transaction.** See correction 1 at the top of this file. The work is to route through that function, not to write it.

Two schema notes that follow from this:

- **`branch_group_members.set_id` is written by a DB trigger.** The schema comment is explicit: *"Denormalized from branch_groups.set_id by a DB trigger — never set this from application code; the trigger overwrites it on insert/update."* Do not set it in an insert.
- **`branch_groups.set_id` is `onDelete: 'set null'`.** Deleting a set does not delete its groups; it orphans them with a null `set_id`. Decide and implement what the UI does with orphaned groups — see criterion 6.

## Acceptance criteria

### 1. New client-scoped write routes

Mirror the admin routes under `/api/portfolio/`, all `requireClientOrAdmin`, all resolving org from `user.organizationId` fresh from the DB (session as fallback), exactly as the other portfolio routes do:

```
POST   /api/portfolio/groups
PATCH  /api/portfolio/groups/:groupId
DELETE /api/portfolio/groups/:groupId
PUT    /api/portfolio/groups/:groupId/members
POST   /api/portfolio/group-sets
PATCH  /api/portfolio/group-sets/:setId
DELETE /api/portfolio/group-sets/:setId
```

Every route must verify the target group or set belongs to the caller's org **before** acting. `enforceOrgScoping` will not do this for you — it resolves communities, not groups.

**Reuse the storage functions the admin routes already call.** The org check belongs in the route; the write logic is shared. Do not fork it.

### 2. "+ New group" works

Clicking it opens an inline form or modal: name, colour, and which set it belongs to. Creates the group and re-renders without a full page reload.

Delete the `// Inert in this slice` comment along with the behaviour it describes.

### 3. Group edit and delete

Each group card and each table row gets edit and delete affordances.

- **Edit** — name, colour, set assignment.
- **Delete** — confirmation naming the group and how many locations it holds. Deleting a group removes its membership rows via cascade; the locations become unassigned in that set, they are not deleted. Say this in the confirmation.

### 4. Membership assignment — the core of the task

From a group, open a location picker listing all org locations with checkboxes, showing for each whether it currently sits in a different group **of the same set**, and which one.

On save, `PUT /api/portfolio/groups/:groupId/members` sets membership to exactly the checked list, and **within one transaction removes those locations from sibling groups in the same set** per the invariant above.

The picker must make the reassignment visible before it happens — "3 locations will move out of West Metro" — rather than silently rearranging another group.

### 5. Group set create, rename, delete

`branch_group_sets` is unique on `(organization_id, name)`. A duplicate name must return a **friendly validation message, not a 500.** Test this explicitly.

Deleting a set nulls its groups' `set_id` rather than deleting them. Either delete the groups too, or surface them as an "Unassigned" section — **pick one, implement it, and state which.** Silently orphaning groups so they vanish from a set-organised page is not acceptable.

### 6. Render cards for every set, not just the first

`renderGroups` calls `renderGroupCards(sets[0])` — only the **first** set gets the card grid. Every other set gets a table and no cards, and the anchor band's coverage bar only ever describes `sets[0]`.

With three sets that is visibly inconsistent. Render the card grid per set, or move cards inside each set panel. The anchor band should either summarise all sets or state which set it is describing.

### 7. Colours come from the shared palette

The colour picker offers the canonical palette plus a custom hex field, writing `branch_groups.color`.

**This overlaps #530.** That task consolidates two conflicting fallback palettes (`.gchip.g1`–`.g5` versus `map.js:118` `_GROUP_PALETTE`, which disagree at index 2 — teal versus green) into one shared module. Whichever lands first creates the module; the second imports it. **Do not create a third palette.**

### 8. Make groups navigable

Clicking a group name goes to Locations filtered to that group. Cheap, and it is the other half of "I can't use this page" — right now the numbers are a dead end.
