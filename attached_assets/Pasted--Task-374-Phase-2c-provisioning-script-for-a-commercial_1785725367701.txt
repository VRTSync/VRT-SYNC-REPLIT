# Task #374: Phase 2c — provisioning script for a commercial organization (seed PNC)

## What & Why

The commercial schema and API exist, but there is no organization in the database and no admin UI to create one (org/branch management UI is a later phase). Provisioning today would mean hand-crafting API calls with an admin session cookie — not repeatable, not reviewable.

This task adds a small, **idempotent** provisioning script — same pattern as `repair-0005.ts` — that creates an organization, its branch communities, its groups, and a client user from a data file. First use: PNC.

## Core principles

- **Idempotent**: safe to run repeatedly. Match on `(organization.name)` and `(organization_id, code)`; update rather than duplicate.
- **Goes through storage functions, not raw SQL**, wherever they exist (`createBranch`, `createBranchGroup`, `setBranchGroupMembers`, `createUser`) so any business logic stays honored.
- **No password in the repo.** The client user's initial password comes from an env var; the script refuses to run without it.
- Data lives in a separate JSON file so future clients are a new file, not new code.

## Done looks like

- `pnpm --filter @workspace/db run provision -- --file=./seeds/pnc.json` (or equivalent script location) creates: 1 organization, 11 branch communities with codes/addresses/cities, 3 branch groups with the right members, and 1 `client_admin` user.
- Re-running changes nothing and reports "already provisioned" per entity.
- `GET /api/portfolio/me` as that client user returns the org, 11 branches, and 3 groups.
- Script prints a summary table (created / updated / skipped counts) and exits non-zero on any failure.
- No secrets committed; README-style usage comment at the top of the script, matching `repair-0005.ts` style.

## Out of scope

- Any UI for org/branch management (later phase).
- Importing historical service data, assets, or map layers for these branches.
- Creating contractor users or assigning HP to the branches (separate step, decide after this lands).
- Changing any existing endpoint or storage function.

### 2. Script — `lib/db/src/provision-org.ts`

- Usage: `DATABASE_URL=… CLIENT_INITIAL_PASSWORD=… pnpm --filter @workspace/db run provision -- --file=./seeds/pnc.json`
- Refuse to run (exit 1, clear message) if `DATABASE_URL` or `CLIENT_INITIAL_PASSWORD` is missing, or if the file path is absent/unreadable.
- Order of operations, each step idempotent:
  1. Organization: find by exact `name`; create if missing, else reuse and report.
  2. Branches: for each entry, find by `(organization_id, code)`; create via the branch-creation path if missing; if present, update `name`/`address`/`city` only when they differ.
  3. Groups: find by `(organization_id, name)`; create if missing. Then resolve `branchCodes` → community ids and set membership (replace-set semantics).
  4. Client user: find by `username`; create with `role='client_admin'`, `organizationId` set, password hashed with bcrypt (cost 10, matching `auth.ts`). If the user exists, **do not touch the password** — report and skip.
- Print a summary: `organization created|reused`, `branches created N / updated N / unchanged N`, `groups …`, `user created|exists`.
- Wrap the whole run in a transaction where practical; on any error, roll back and exit non-zero.

### 3. Package script

Add to `lib/db/package.json`: `"provision": "tsx src/provision-org.ts"`.

### 4. Verify

- Run against dev twice. First run creates everything; second reports all reused/unchanged and makes no writes (verify with row counts before/after).
- `SELECT c.code, c.name, c.city FROM communities c JOIN organizations o ON o.id=c.organization_id WHERE o.name='PNC Bank' ORDER BY c.code;` → 11 rows.
- Group membership: 6 / 3 / 2 branches respectively.
- Log in as the client user → `GET /api/portfolio/me` returns org + 11 branches + 3 groups; `GET /api/portfolio/dashboard` returns zeros (no service data yet) without errors.
- Confirm as an HOA/PM/contractor user that these 11 branches do **not** appear in their community lists.
