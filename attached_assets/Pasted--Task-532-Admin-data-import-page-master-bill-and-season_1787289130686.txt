# Task #532: Admin data import page — master bill and seasonal contract

*Supersedes the CLI delivery in #525 and #518. **The parsing, validation and write logic in those specs is unchanged** — only the entry point moves from a shell script to an admin page.*

## What & Why

#525 and #518 were written as CLI scripts on the assumption that someone could run them against production. **That assumption is false.** Verified 2026-08-20:

| | Host | Database | PNC data |
|---|---|---|---|
| Repl shell | `helium` | `heliumdb` | none — zero `FB%` communities |
| Deployed app | `169.254.254.254` (Neon proxy) | `neondb` | the real org |

A script run from the shell writes to the dev database and the client sees nothing. Reaching production from the shell means putting a production credential into the dev Repl and routing around a link-local proxy address that likely isn't reachable from there anyway.

**The deployed app is already connected to production.** An admin page uploads the file, the server parses and writes it. The production problem disappears rather than being worked around, and there is no credential to add or remember to remove.

It is also reusable. The next client's history gets imported through a screen instead of a one-off script and a runbook.

## This follows an existing, proven pattern — do not invent a new one

`admin/pages/contract-import.js` (625 lines) already implements exactly this shape: a 4-step wizard — Upload → Map → Preview → Commit — with a dropzone, a file input accepting `.xlsx/.csv/.xls`, and a community selector. It is registered in `admin-shell.html:140`.

It is backed by three routes, all `requireAdmin`:

```
POST /api/admin/import/contract-tasks/parse     4614   multer upload.single("file") → parseFile()
POST /api/admin/import/contract-tasks/preview   4628   → generatePreview()
POST /api/admin/import/contract-tasks/commit    4652   → commitImport()
```

**Copy this structure.** Same three-endpoint split, same stepper, same visual language. A reviewer should recognise the new page as a sibling of the existing one.

## Two importers, one page, two modes

| Mode | Source | Writes | Spec |
|---|---|---|---|
| **Master bill** | 3 bill workbooks, one at a time | 139 invoices, 110 tasks + completions | #525 |
| **Seasonal contract** | contract task list | 33 schedules, 638 visits, 165 tasks, 88 completions | #518 |

A mode selector at the top. Everything below adapts.

**Master bill is 3 steps, not 4** — the sheet layout is fixed (header row 4, data row 5, nine known columns), so there is no column-mapping step. Upload → Preview → Commit.

## Acceptance criteria

### 1. Reuse the validation logic exactly as specced

Whatever #525 and #518 built for parsing, the mapping table, date normalisation, contract-line filtering, the First Bank assertion, idempotency keys and the sibling-removal transaction — **all of it moves behind the routes unchanged.**

If those tasks produced `scripts/src/import-master-bill.ts`, extract the logic into a module both a route and the script can call. **Do not fork it, and do not reimplement the validation in the route.** Every assertion in #525 and #518 still applies; it now reports to a browser instead of a terminal.

State clearly which files were extracted and what now calls them.

### 2. Three routes per mode, all `requireAdmin`

```
POST /api/admin/import/master-bill/parse     upload.single("file") → parsed rows + detected period
POST /api/admin/import/master-bill/preview   → the full dry-run report as JSON
POST /api/admin/import/master-bill/commit    → performs the import, returns the summary

POST /api/admin/import/seasonal/parse
POST /api/admin/import/seasonal/preview
POST /api/admin/import/seasonal/commit
```

**`requireAdmin`, never `requireClientOrAdmin`.** These write bulk history across an entire organization. A client must never reach them.

**Preview must never write.** It is the dry run. Confirm this by watching row counts across a preview call.

### 3. The preview step shows the dry-run report, in full

Everything the CLI report was specified to print, rendered as a screen:

- **The community mapping table** — every PNC code → resolved community name. **Prominent, not collapsed.** A wrong mapping files real service history against the wrong bank branch and looks entirely normal afterwards. This is the one thing a human must read, so the UI must make reading it unavoidable.
- Skipped rows with line numbers and the reason
- Date-normalised rows, with a count
- Contract-only rows, with a count
- The resolved service account, by name — and whether it existed or would be created
- Per-branch counts and totals

**Assertions that would abort the CLI must block the Commit button**, with the failure stated plainly. Expected values are in #525 (3 skipped / 20 normalised / 29 contract-only / 139 / 110 / $53,120.90) and #518 (18 rows, all 2026 starts, per-branch 3/58/15/8).

### 4. Commit is deliberate

Commit is disabled until a preview has run against the currently uploaded file. Re-uploading resets it.

A confirmation dialog states what is about to be written, in counts, and that it targets production.

After commit: the summary, and **the undo instruction, on screen, copyable.**

### 5. Idempotency is unchanged and still holds

Re-uploading and committing the same file adds nothing. The keys are already specced — `invoices_source_line_unique_idx` and `tasks.import_fingerprint` for #525, `(schedule_id, service_date)` and `schedule_instance_key` for #518.

**Test this through the UI**, not just the script.

### 6. Batch history and undo

A panel listing prior import batches — label, date, row counts, who ran it.

Include an undo per batch, behind a typed confirmation. This is the reversibility #525 and #518 require, made usable by someone who is not going to run SQL.

### 7. Nav and registration

Add the page to the admin nav near the existing Contract Import entry. Register the script in `admin-shell.html` alongside `contract-import.js`.

Name it something a human would recognise — **"Data Import"** or **"Seed Import"** — and label the two modes clearly.

## Out of scope

- Scheduled or automated imports.
- Importing anything other than these two formats.
- Editing rows in the preview before committing — fix the spreadsheet and re-upload.
- A client-facing version of this page.

## Note on sequencing

If #525 and #518 have already shipped as scripts, **this task wraps them rather than replacing them.** Keeping the CLI is fine — it is useful for testing against dev. What matters is that both paths call one implementation, so a fix to a validation rule cannot land in one and miss the other.
