# Task #343: Platform-scale admin dashboard aggregate endpoint

**What/why:** The admin dashboard is being rebuilt as a super-admin ops console (see mockup `admin-dashboard-v4.html`). It needs one aggregate endpoint that returns platform totals, exception counts, and trend data — designed so every number stays a single SQL aggregate that scales to thousands of communities. No per-community rows in this payload.

## Acceptance criteria

1. New route `GET /api/admin/dashboard` (requireAdmin) in `routes/routes.ts`, backed by a new `getAdminDashboard()` in `storage.ts`. Response shape:

```json
{
  "totals": {
    "communities": 0, "communitiesOnboarding": 0, "communitiesAddedThisMonth": 0,
    "activeAssets": 0, "assetsAddedThisMonth": 0,
    "incompleteAssets": 0, "completenessPct": 0.0,
    "mapLayers": 0
  },
  "exceptions": {
    "communitiesWithOverdueWork": 0,
    "requestsUnacknowledged48h": { "count": 0, "oldestDays": 0 },
    "communitiesQuiet14d": 0,
    "onboardingStalled30d": 0
  },
  "activityTrend": [ { "weekStart": "2026-06-01", "completed": 0, "stillOpen": 0 } ],
  "reliability": {
    "onTimeServicePct30d": 0.0, "missedServices30d": 0,
    "photoProofPct30d": 0.0
  },
  "business": {
    "invoicedThisMonthCents": 0,
    "unpaidOver30dCents": 0, "unpaidOver30dCount": 0,
    "contractsExpiring60d": 0, "contractsExpiredUnrenewed": 0
  },
  "completenessDistribution": [ { "bucket": "98-100", "communities": 0 }, ... ],
  "users": { "active30d": 0, "contractorsActive7d": 0, "hoaMembersAddedThisMonth": 0 }
}
```

2. Definitions (implement as SQL aggregates, one query per section max):
   - *overdue work*: tasks with `dueDate < now()` and not completed. Communities count = `COUNT(DISTINCT communityId)`.
   - *unacknowledged request*: HOA-submitted task with status `submitted` older than 48h.
   - *quiet community*: no task completion, service visit, or asset note in 14 days. Use `MAX()` over existing timestamps — do NOT add a lastActivity column in this task.
   - *onboarding stalled*: community with completeness < 90% and no assets created in 30 days.
   - *activity trend*: last 8 ISO weeks of task completions (`task_completions.completedAt`), plus count of tasks created that week still open.
   - *on-time service*: service_visits matched to service_schedules within the scheduled window; missed = scheduled with no visit. If the current schema can't express "missed" cleanly, return `null` for those two fields and note it in the PR description — do not invent placeholder math.
   - *photo proof*: completions having ≥1 attachment / total completions, 30d.
   - *money*: sums off `invoices` (`status != 'paid'` + age for unpaid); `contracts` end dates for expiring/expired.
   - *completeness distribution*: per-community complete-asset ratio bucketed into 98-100 / 90-98 / 70-90 / <70. This is the one per-community scan — acceptable for now; add `LIMIT`-free aggregate only (no rows returned).
3. Single round trip; every aggregate uses indexed columns where possible. Add indexes only if a query plan clearly needs one, as a migration file under `lib/db/migrations/` (never `drizzle-kit push`; rebuild server after adding).
4. Existing `/api/admin/summary` stays untouched (mobile admin screen uses it).
5. Response cached in-process for 60 seconds (simple module-level cache) — this endpoint will be hit on every admin dashboard load.

## Files involved

- `artifacts/api-server/src/routes/routes.ts`, `artifacts/api-server/src/storage.ts`
- Possibly one migration under `lib/db/migrations/` (indexes only)

## Must NOT change

- `/api/admin/summary`, any existing route or schema column.
- No new schema columns in this task (ack-timestamp and richer activity tracking are a future task).

## How to verify

- `curl` as admin returns the full shape with plausible numbers against dev data; non-admin gets 403.
- Every section returns in <500ms on dev data (log timings).
- `pnpm run typecheck` passes; server rebuilds and boots.
