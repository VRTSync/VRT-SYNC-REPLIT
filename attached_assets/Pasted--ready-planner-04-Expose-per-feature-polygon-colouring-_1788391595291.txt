# ready-planner-04: Expose per-feature polygon colouring on the shared map renderer

*Awaiting a number. Spec 04 of 10 — see [`ready-planner-00-index.md`](ready-planner-00-index.md).*
*Self-contained. No other spec needs to land first.*

## What & Why

Every map in the web portals is drawn one of two ways, and they have diverged:

| Implementation | Where | Used by |
|---|---|---|
| **`lib/leaflet-template` + `VRTMapRenderer`** — an iframe driven over `postMessage` | `artifacts/web-portal/public/common/map-render.js` | portal dashboard, portal map, portfolio dashboard, portfolio map, portfolio branch-detail — **5 pages** |
| Direct in-page Leaflet | `admin/pages/xeriscape-planner.js:1046`, `:1668` | the xeriscape planner only |

The planner is being migrated onto the shared renderer so the app has **one** way of drawing maps. The blocker is that the planner colours **each polygon individually** — selected, group-highlighted, or neither — and `VRTMapRenderer`'s public API has no way to do that.

**The capability already exists on both sides of the bridge. It is simply not exposed.**

- The iframe implements it: `lib/leaflet-template/src/index.ts:802` —
  `updateLayerColorMap(layerId, colorMap, fallbackColor)` looks up `colorMap[featureId]` per feature and calls `setStyle({ color, fillColor })` on each. The geoJSON `style` callback at `:348` resolves the same map on first render.
- The client already sends it: `map-render.js:747` calls
  `_cmd('updateLayerColorMap', ctrlLayer.id, updMap, fallback)` for irrigation controllers.
- But the returned public object (`map-render.js:788-806`) exposes only
  `load, setActiveCategory, setVisibleSubLayers, setSatellite, fit, invalidateSize, on, applyColorLive, addCustomLayer, showCustomLayers, destroy`.

So this spec adds a thin public wrapper around a command the renderer already sends, and confirms the click event carries what a caller needs.

## Acceptance criteria

**Add `setFeatureColors`**

- [ ] Add to the object returned by `create()` in `map-render.js` (`:788-806`):

```js
/**
 * Recolour individual features within a custom layer.
 * @param {string} layerId    id used when the layer was added via addCustomLayer
 * @param {Object} colorMap   { featureId: '#rrggbb' }
 * @param {string} fallback   colour for features absent from colorMap
 */
function setFeatureColors(layerId, colorMap, fallback) {
  _cmd('updateLayerColorMap', layerId, colorMap || {}, fallback);
}
```

- [ ] It must queue like every other command if the iframe has not reported `mapReady` yet — use the same `_cmd` path, do not bypass it.
- [ ] Calling it with an unknown `layerId` is a no-op, not an error.
- [ ] Calling it repeatedly is cheap — it recolours in place and must **not** re-add or re-render the layer.

**Confirm the click payload**

- [ ] `VRTMapRenderer` emits `assetTap` (`map-render.js:133`) via `on('assetTap', handler)`. Verify the payload carries a **feature identifier that matches the keys used in `colorMap`**.
- [ ] If it does not, extend the payload in `lib/leaflet-template/src/index.ts` so it does — **additively**, keeping every existing field. Do not work around it by reverse-looking-up coordinates in the page.
- [ ] Document the payload shape in a comment at the `on()` definition, since the next caller will need it.

**Keep it additive**

- [ ] **No existing signature changes.** `applyColorLive`, `sendBranchPins`, `addCustomLayer`, `showCustomLayers`, `load`, `fit` all behave exactly as before.
- [ ] `sendBranchPins`'s default colour rule at `map-render.js:828` is untouched — it falls back to the open-work-order amber rule when no `colorFor` is passed, and the dashboard relies on that.
- [ ] No change to how any of the five existing map pages call the renderer.

## Files likely involved

- `artifacts/web-portal/public/common/map-render.js` — new method, additive
- `lib/leaflet-template/src/index.ts` — **only** if the `assetTap` payload needs a feature id

## What must NOT change

- **The five live map pages**: portal dashboard, portal map, portfolio dashboard, portfolio map, portfolio branch-detail.
- `sendBranchPins` default behaviour — the dashboard's amber pins are a #545 regression test.
- `applyColorLive` and the irrigation controller/zone colour path that already uses `updateLayerColorMap` internally.
- The xeriscape planner — it is **not** touched by this spec.

## How to verify

- [ ] Add a temporary custom polygon layer on any portfolio page, call `setFeatureColors(id, { someFeatureId: '#ff0000' }, '#cccccc')` from the console → that one polygon turns red, the rest grey.
- [ ] Call it again with a different map → colours update **without** the map flickering or refitting bounds.
- [ ] Call it before the iframe is ready → the command is queued and applied once `mapReady` fires.
- [ ] Call it with a nonexistent `layerId` → nothing happens, no console error.
- [ ] `on('assetTap', fn)` fires on polygon click and the payload contains an id that can be used as a `colorMap` key. Log it and confirm the round trip.
- [ ] **Regression pass on all five existing map pages**, screenshots before and after:
  - portal dashboard, portal map
  - portfolio dashboard — **amber pins for open work orders unchanged**
  - portfolio map — group colours and layer bars unchanged
  - branch detail — sub-layer colours unchanged
- [ ] Console clean on every one of them.
- [ ] `grep -n "setFeatureColors" artifacts/web-portal/public/common/map-render.js` → present in the returned object. **Confirm the file is present before trusting the result** — a negative grep on a partial checkout proves nothing, and that has produced false findings on this project twice.
