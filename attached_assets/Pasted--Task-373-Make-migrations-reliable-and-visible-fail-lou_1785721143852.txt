# Task #373: Make migrations reliable and visible (fail loudly, handle enums, status endpoint)

## What & Why

Migrations are not reliably reaching the database. The mechanism exists — `index.ts` calls `runMigrations()` at boot and `build.mjs` copies `lib/db/migrations/` into `dist/migrations/` — but failures are swallowed:

```ts
catch (err) {
  logger.error({ err }, "Drizzle migrations failed — continuing without schema update");
}
```

The server then boots normally against a stale schema, and nothing surfaces anywhere. Three recent migrations (`0005`, `0006`, `0007`) may or may not have applied; there is no way to tell from the app.

Suspected root cause for enum migrations specifically: `ALTER TYPE … ADD VALUE` cannot run inside a transaction block, and Drizzle's migrator wraps migration execution in one. `0005` (adds `client_admin`) and `0007` (adds five `service_type` values) are exactly this shape.

This task makes migration state **correct, loud, and visible**. It does NOT add any UI that executes migrations.

## Done looks like

- Boot in production **fails fast** if migrations error — the process exits non-zero rather than serving traffic against a stale schema. Development keeps the current permissive behavior but logs at error level with an unmissable marker.
- Enum `ADD VALUE` statements apply successfully (verified: `service_type` has 6 values, `user_role` includes `client_admin`).
- `GET /api/admin/migrations` (requireAdmin) returns applied-vs-available migration state.
- The admin hub shows that state read-only — **no "run migrations" button anywhere**.
- Verified against the real database: `SELECT * FROM drizzle.__drizzle_migrations` lists 0000–0007.

## Out of scope

- Any UI or endpoint that triggers, re-runs, or rolls back migrations.
- Changing existing migration files' contents (except as needed for the enum-transaction fix described below).
- The Layer 2 `runStartupMigrations()` ALTER safety-net block — leave as is.
- Phase 3 portal work.

## Steps

### 1. Diagnose first, then fix — report findings before changing behavior

Run against the dev database and record the output in the implementation notes:

```sql
SELECT * FROM drizzle.__drizzle_migrations ORDER BY created_at;
SELECT unnest(enum_range(NULL::service_type));
SELECT unnest(enum_range(NULL::user_role));
```

State plainly which of 0005/0006/0007 are applied and whether the enum values exist. If they all applied cleanly, say so — the fixes below still apply, but the "enum in transaction" theory can be dropped.

### 2. Enum statements must run outside the migrator transaction

If (and only if) the diagnosis shows enum migrations failing:

- Split enum `ADD VALUE` statements out of the transactional path. Options, pick one and justify it in the notes:
  - Run them via a small pre-migration step in `runMigrations()` that executes any `ALTER TYPE … ADD VALUE` statements found in pending files using `pool.query` directly (autocommit), before handing the rest to Drizzle's migrator; or
  - Keep them in the migration files but have `lib/db/src/migrate.ts` execute files containing `ADD VALUE` outside the transaction.
- Whatever the approach, it must stay idempotent (`IF NOT EXISTS`) and must not require editing already-applied migration files' checksums — do not break Drizzle's journal/hash tracking.

### 3. Fail fast in production — `artifacts/api-server/src/index.ts`

Replace the swallow-and-continue block:

```ts
try {
  appliedCount = await runMigrations(pool, migrationsFolder);
  logger.info({ applied: appliedCount }, `applied ${appliedCount} migrations`);
} catch (err) {
  if (process.env.NODE_ENV === "production") {
    logger.fatal({ err }, "MIGRATIONS FAILED — refusing to start with a stale schema");
    process.exit(1);
  }
  logger.error({ err }, "MIGRATIONS FAILED (dev) — continuing with a stale schema");
}
```

Keep the existing log fields (`elapsedMs`, `applied`). Do not change Layer 2 behavior.

### 4. Status endpoint — `GET /api/admin/migrations` (requireAdmin)

```json
{
  "applied": [ { "tag": "0007_extend_service_type_enum", "appliedAt": "..." } ],
  "available": [ "0000_baseline", "…", "0007_extend_service_type_enum" ],
  "pending": [],
  "inSync": true
}
```

- `applied` from `drizzle.__drizzle_migrations`; `available` from the journal (`meta/_journal.json`) shipped in `dist/migrations`; `pending` = available − applied.
- Read-only. No POST/PATCH. No side effects.

### 5. Admin hub display (read-only)

- Add a small panel to the admin dashboard page (or the account/settings page — pick whichever fits the existing IA and say which) showing: migration count applied, pending count, and a red state when `inSync` is false listing the pending tags.
- Use the shared `VRTUtils.esc` helper and the existing panel styling. No button that runs anything.

### 6. Verify

- Force a failure locally (e.g. temporarily point at a DB missing a prerequisite) and confirm: production mode exits non-zero; dev mode logs the loud marker and continues.
- With a healthy DB: boot logs `applied N migrations`, `GET /api/admin/migrations` returns `inSync: true`, `pending: []`.
- Confirm in SQL that `service_type` has all 6 values and `user_role` includes `client_admin` after boot.
- Re-boot twice: second boot applies 0 migrations and stays in sync.
- `pnpm run typecheck` passes; do NOT disable any compiler options to achieve this.
