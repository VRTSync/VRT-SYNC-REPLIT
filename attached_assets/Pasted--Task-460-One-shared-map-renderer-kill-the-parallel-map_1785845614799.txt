# Task #460: One shared map renderer — kill the parallel map implementation

## What & Why

The client portal's branch maps render **plain colored dots**, while the production community map renders lettered controller badges, controller-colored zone rings, and the paw pet-station markers. Same platform, same data, two different looks.

Cause: two independent implementations.

- `portal/pages/map.js` (1,233 lines) fetches `GET /api/communities/:id/controllers` and drives the rich marker APIs — `setControllerMarkers`, `setZoneMarkers` — plus the icon handling in the leaflet template's `pointToLayer`.
- `portfolio/pages/branch-detail.js` (1,327 lines) fetches **no controller data at all** (`grep controllers` → 0 hits) and only calls `addLayers` with raw GeoJSON, which falls through to generic `L.circleMarker`.

**This is a parallel system and it should not exist.** All map surfaces in this app must render through one implementation, so configured colors, icons, marker styles, popups, and behavior are identical everywhere by construction — not by two teams remembering to keep them in step.

## The fix: extract, don't duplicate

Create **one shared map renderer** used by every web map surface. Differences between portals are limited to (a) where the data comes from and (b) surrounding page chrome — never to how things are drawn.

### New module: `artifacts/web-portal/public/common/map-render.js` → served at `/common-static/map-render.js`

Exposes a single factory:

```js
window.VRTMapRenderer = {
  create(opts) -> instance
}
```

`opts`:
- `iframe` — the existing map iframe element (**the renderer never creates, moves, or re-parents it**; see the hazard note in `branch-detail.js`)
- `adapter` — data functions supplied by the caller (see below)
- `hierarchy` — the `LAYER_HIERARCHY` definition (labels, order, default colors)

Instance methods (the whole rendering surface):
- `load(communityId)` — fetch layers + controllers via the adapter, push outline, layers, and markers
- `setActiveCategory(key)` / `setVisibleSubLayers(ids)`
- `setSatellite(bool)`
- `fit()` / `invalidateSize()`
- `on('assetTap' | 'ready', handler)`

**Adapter interface** — the only portal-specific part:

```js
{
  fetchLayers(communityId)        -> Promise<layer[]>       // includes color, layerKey, subLayerKey
  fetchLayerGeojson(layer)        -> Promise<geojson|null>
  fetchControllers(communityId)   -> Promise<controller[]>  // controllers with zones
}
```

- **Portal adapter** (HOA/PM/contractor): `/api/map-layers?communityId=`, `/api/map-layers/:id/geojson`, `/api/communities/:id/controllers`
- **Portfolio adapter** (client): the org-scoped portfolio endpoints, plus a **new** `GET /api/portfolio/branches/:communityId/controllers` (`requireClientOrAdmin`, org-verified) returning the same shape as the existing controllers endpoint. Do not loosen the existing endpoint's membership rules — add the org-scoped sibling, exactly as was done for layer geojson.

### Rendering rules the module owns (single implementation)

1. **Controllers** → `setControllerMarkers` (lettered badge in the controller's color).
2. **Zones** → `setZoneMarkers`, colored by parent controller.
3. Geometry suppression rule already established: withhold controller/zone geometry **only when marker data actually exists** (non-empty marker set) — same rule the portal map and mobile now use.
4. **Other point types** → the template's `pointToLayer`, including the pet-station paw and any future icons.
5. **Colors**: `map_layers.color` → hierarchy default for that sub-layer → neutral grey. Never a tab-accent palette.
6. Outline drawn as neutral context, never a toggleable layer.

## Done looks like

- A bank branch map is **visually identical** to a Miramonte community map for the same asset types: lettered controller badges, controller-colored zone rings, paw pet-station markers, same popups, same colors.
- `portal/pages/map.js` and `portfolio/pages/branch-detail.js` both delegate all rendering to `VRTMapRenderer`; neither contains its own `addLayers` / `showLayerIds` / marker-push logic. Page files keep only chrome: panels, tabs, toggles, inventory tables.
- Portfolio Map page (`portfolio/pages/map.js`) also uses the shared module for its pin rendering where applicable.
- New `GET /api/portfolio/branches/:communityId/controllers` returns the same shape as the community controllers endpoint, org-scoped; cross-org → 403.
- Behavior of the existing HOA/PM/contractor map is unchanged — verify against screenshots before/after.
- No duplicated rendering code remains: `grep -n "setControllerMarkers\|setZoneMarkers\|addLayers" artifacts/web-portal/public` shows those calls **only** inside `common/map-render.js`.

## Steps

1. **Write the module** by extracting the proven logic from `portal/pages/map.js` — layer push, visibility sync, controller/zone marker building and color maps, outline handling, fit behavior, satellite. Do not rewrite it; move it. Keep the existing `cmdToIframe` handshake and `mapReady` pattern.
2. **Portal map** refactor: replace its internal rendering with `VRTMapRenderer` + the portal adapter. The layers panel, category pills, color pickers, and detail panel stay in the page file.
3. **API**: add the org-scoped controllers endpoint for the portfolio.
4. **Portfolio branch detail** refactor: replace its rendering with `VRTMapRenderer` + the portfolio adapter. Keep the stable-iframe mount, the category tabs, sub-layer toggles, and expand-in-place from #457 — these are chrome, and they call into the module.
5. **Portfolio map page**: adopt the module for pin rendering.
6. **Shell script tags**: load `/common-static/map-render.js` before page scripts in `portfolio-shell.html`, `hoa-shell.html`, `pm-shell.html`, `contractor-shell.html`. `/common-static` is already in `artifact.toml` paths.
7. **Verify**
   - Side-by-side screenshots: Miramonte (portal map) and FB02 (portfolio) — controller badges, zone colors, pet-station markers, and popups match in style.
   - HOA/PM/contractor map behaves exactly as before (category switching, sub-layer toggles, color pickers, asset detail panel).
   - Portfolio: category tabs, sub-layer toggles, expand-in-place, and satellite all work through the module.
   - Cross-org controllers request → 403.
   - The grep in "Done looks like" passes.
